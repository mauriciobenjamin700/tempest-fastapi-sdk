    Mercado Pago: testing webhooks¶

    Webhooks are the hardest part of a payment integration to test: Mercado Pago calls you, not the other way around, and it needs a public URL to call. This page shows four levels of testing, from what runs with no network at all to the real delivery:

    1. Simulated by the SDK, no network — the Orders API and the notification are simulated; the real adapter creates, re-reads and refunds over them. No credential, no sandbox. Start here — in the test suite and for manual testing.
    2. Signed simulation over the sandbox — you sign a notification with your secret and deliver it to your route. The route re-reads a real sandbox order. No public URL needed.
    3. The dashboard's "simulate notification" — Mercado Pago sends a test notification to your URL.
    4. Real delivery — you create an order and Mercado Pago notifies on its own.

    First, have the credentials from the test accounts and credentials recipe at hand, and know what the route does from Mercado Pago »: it verifies the signature and re-reads the order, because the notification does not carry the payment's state.

    Level 1 — simulated by the SDK, no network¶

    The SDK ships Mercado Pago simulated in tempest_fastapi_sdk.testing.fakes:

    • FakeMercadoPagoOrdersAPI answers /v1/orders with state — create (idempotent on X-Idempotency-Key), read, cancel, capture and refund. It is an httpx handler, so the real MercadoPagoPixProvider runs over it unchanged: MercadoPagoPixProvider(api.http_client()).
    • The moves only the provider makes are methods — pay, expire, fail, cancel, capture, refund — and each returns the signed notification announcing the new state, ready for delivery.send(client, route).
    • build_mercado_pago_delivery(order, secret=...) builds the notification on its own, in the shape of the real delivery observed in production, signed by the same sign_manifest the SDK's verifier uses.

    The script creates charges through the adapter, moves each one and delivers the notification to the route mounted the way your service mounts it:

    import asyncio
from typing import Any

import httpx
from fastapi import Depends, FastAPI

from tempest_fastapi_sdk.integrations.payment import PixChargeRequest, PixPayer
from tempest_fastapi_sdk.integrations.payment.adapters import (
    MercadoPagoOrderDelivery,
    MercadoPagoPixProvider,
    make_mercado_pago_webhook_delivery_dependency,
)
from tempest_fastapi_sdk.testing.fakes import (
    FakeMercadoPagoOrdersAPI,
    MercadoPagoDelivery,
)

SECRET: str = "local-test-secret"


def build_app(provider: MercadoPagoPixProvider) -> FastAPI:
    """Mount the webhook route exactly as the service would."""
    app = FastAPI()
    dependency = make_mercado_pago_webhook_delivery_dependency(SECRET, provider)

    @app.post("/webhooks/mercado-pago")
    async def webhook(
        delivery: MercadoPagoOrderDelivery = Depends(dependency),
    ) -> dict[str, Any]:
        """Report what the re-read decided."""
        event = provider.parse_webhook(delivery)
        return {
            "type": event.type.value,
            "status": event.charge.status.value if event.charge else None,
        }

    return app


async def deliver(app: FastAPI, delivery: MercadoPagoDelivery) -> tuple[int, Any]:
    """Send one signed delivery to the route, in-process."""
    async with httpx.AsyncClient(
        transport=httpx.ASGITransport(app=app), base_url="http://local"
    ) as client:
        answer = await delivery.send(client, "/webhooks/mercado-pago")
    return answer.status_code, answer.json()


async def main() -> None:
    """Run payment, refund, cancellation and expiry with no network."""
    api = FakeMercadoPagoOrdersAPI(webhook_secret=SECRET)
    provider = MercadoPagoPixProvider(api.http_client(), action_retry_delays=())
    app = build_app(provider)
    payer = PixPayer(email="buyer@example.com")

    async def new_charge(reference: str) -> str:
        """Create a R$ 19,90 Pix charge through the real adapter."""
        charge = await provider.create_pix_charge(
            PixChargeRequest(amount_cents=1990, reference=reference, payer=payer)
        )
        return charge.provider_charge_id

    paid = await new_charge("order-1")
    print("created   ", await deliver(app, api.delivery(paid)))
    print("paid      ", await deliver(app, api.pay(paid)))
    await provider.refund_pix_charge(paid, 500, refund_reference="refund-1")
    print("partial   ", await deliver(app, api.delivery(paid)))
    await provider.refund_pix_charge(paid, refund_reference="refund-2")
    print("refunded  ", await deliver(app, api.delivery(paid)))

    cancelled = await new_charge("order-2")
    await provider.cancel_pix_charge(cancelled)
    print("cancelled ", await deliver(app, api.delivery(cancelled)))
    print("expired   ", await deliver(app, api.expire(await new_charge("order-3"))))

    stranger = FakeMercadoPagoOrdersAPI(webhook_secret="another-secret")
    await MercadoPagoPixProvider(stranger.http_client()).create_pix_charge(
        PixChargeRequest(amount_cents=1990, reference="x", payer=payer)
    )
    print("forged    ", await deliver(app, stranger.delivery(stranger.order_ids[0])))
    other = FakeMercadoPagoOrdersAPI(webhook_secret=SECRET)
    await MercadoPagoPixProvider(other.http_client()).create_pix_charge(
        PixChargeRequest(amount_cents=1990, reference="y", payer=payer)
    )
    print("simulated ", await deliver(app, other.delivery(other.order_ids[0])))


asyncio.run(main())

    In your test suite

    The same code becomes a test: swap the prints for asserts. The SDK's suite does exactly that in tests/integrations/payment/adapters/test_mercado_pago_simulated_flow.py — Pix paid, refunded in two steps, cancelled, expired, and card approved, authorized then captured, and declined (api.decline_next_card()).

    What the simulation copies, and what it assumes

    The state of each transition, the status codes (201, 200, 402, 404), the idempotency rule and 409 cannot_refund_order were copied from the sandbox. The notification's shape was copied from one real delivery, order.canceled. The other actions (order.processed, order.refunded, order.failed, order.action_required) were not observed and are not in the document the SDK vendors either, which only lists order.created / order.updated: the simulator names them after the order's status. The SDK's route does not decide on the action — it re-reads the order — so this does not change the outcome; it only matters if your code reads action.

    Assumed, not copied: 409 cannot_cancel_order (and its message "The order cannot be canceled in status …"), the code and message of the 404 for an unknown order (order_not_found, "Order … not found" — only the 404 status was measured) and the 400 invalid_refund_amount for a refund above the balance, with its message. If your code reads code or message from these answers, check them in the sandbox.

    Manual testing: the service running, Mercado Pago simulated¶

    The same simulator runs as a server, and the service points at it through MERCADOPAGO_BASE_URL (a MercadoPagoSettings field, default https://api.mercadopago.com). A minimal service, with a route that creates a charge and the webhook route:

from tempest_fastapi_sdk import HTTPClient
from tempest_fastapi_sdk.integrations.payment import PixChargeRequest, PixPayer

    MercadoPagoOrderDelivery,
    MercadoPagoPixProvider,
    make_mercado_pago_webhook_delivery_dependency,

from tempest_fastapi_sdk.settings import MercadoPagoSettings

settings = MercadoPagoSettings()
provider = MercadoPagoPixProvider(HTTPClient(**settings.mercado_pago_kwargs()))
app = FastAPI()
webhook_dependency = make_mercado_pago_webhook_delivery_dependency(
    settings.MERCADOPAGO_WEBHOOK_SECRET, provider

@app.post("/charges")

    The secret never goes on the command line

    simulate-webhook has no --secret option: the value would land in the shell history and in ps. It reads from a variable (--secret-env, default MERCADOPAGO_WEBHOOK_SECRET) or a file (--secret-file), and never prints the value — without it, it exits with code 2 naming which variable was missing.

    MERCADOPAGO_BASE_URL off the default is a production violation

    The access token goes to the host this field names. In a Settings composing EnvironmentSettings, with ENV=production, any value other than https://api.mercadopago.com enters production_violations() and building the Settings raises ValidationError (MERCADOPAGO_BASE_URL: not the Mercado Pago API host).

    Without --fake-api, the command signs just the id (--order-id) or the order from a file (--order-json). Against a service that re-reads the order from the real Mercado Pago, a made-up id gets 404 on the re-read — the simulated case above.

    The ready-made route: make_mercado_pago_router¶

    The webhook route above is the same in every service: verify, re-read, hand over to your code, answer 200. make_mercado_pago_router mounts that route on top of the make_mercado_pago_webhook_delivery_dependency dependency — the verification and the re-read are the same — and you write only the handler:

    app.include_router(make_mercado_pago_router(provider, on_delivery=handle, settings=settings, simulate=settings.ENV == "development")) — the complete service is in the Front end in development example, right below.

    • on_delivery(delivery: MercadoPagoOrderDelivery) -> Awaitable[None] receives the verified delivery with the order re-read. It returns: the route answers 200 with {"ok": true, "data_id": ..., "order_status": ...}. It raises: the answer is 500 — and, per the provider's documentation, Mercado Pago delivers again (redelivery expected, not observed here).
    • The secret comes from secret=; without it, from settings.MERCADOPAGO_WEBHOOK_SECRET (or from the environment and .env when settings is missing too). An empty secret is refused at construction (ValueError): it would reject every delivery.
    • webhook_path defaults to /webhooks/mercado-pago — the URL you register in the dashboard.
    • A service that already writes the route by hand with the dependency keeps working: nothing changed in it.

    Front end in development: simulate=True¶

    With simulate=True, the router also mounts the routes a front end uses to do what only Mercado Pago does — pay, expire, fail, cancel, capture, refund:

    Route What it does
    GET /dev/mercado-pago/orders every order of the simulator
    GET /dev/mercado-pago/orders/{order_id} one order; 404 when unknown
    POST /dev/mercado-pago/orders/{order_id}/{transition} pay, expire, fail, cancel, capture, refund (?amount_cents= for a partial refund)

    Each transition moves the order in the in-memory FakeMercadoPagoOrdersAPI your provider runs over, signs the notification with the route's secret and delivers it to the service's own webhook route, through the whole app (httpx.ASGITransport(request.app)): middleware, signature check, re-read and on_delivery all run for real. The answer carries the order after the transition and what the webhook route answered. A transition the state does not allow (refund before payment) is 409; an unknown order, 404; an unknown transition, 422. In Swagger these routes show under the mercado-pago (dev) tag.

    {order_id} also takes the external_reference you sent on create — the reference of PixChargeRequest, usually your correlation_id, which is what your screens and logs show. When several orders share it, the most recent one is moved: charging the same reference again after an expiry means the new order.

    The provider is tied to the simulator by mercado_pago_provider_for: with simulate=False it returns the MercadoPagoPixProvider over settings.mercado_pago_kwargs(); with simulate=True, the same adapter over an in-memory FakeMercadoPagoOrdersAPI, and the router finds the simulator on its own (simulation_api_for(provider)). For cards, provider_class=MercadoPagoCardProvider; for another simulator, simulation_api=.

    API and worker in separate processes: simulation_url¶

    The simulate=True simulator lives in the memory of one process. If your service has a worker (TaskIQ, a cron) that re-reads the order — the sweep of pending charges, the refund job — the order created in the API's request does not exist for it.

    Manual withdrawal¶

    Mercado Pago's payout is not enabled for the account (#499). Meanwhile, the router pays withdrawals through an administrator: with withdraw=, it mounts POST /api/mercado-pago/withdraw, which:

    1. debits the user's whole available balance through WalletService.withdraw — the route takes no amount, the wallet ends at zero;
    2. writes the PENDING row of the manual payout table (make_manual_payout_model), with the key masked;
    3. e-mails the administrator the amount, Pix key and type, user_id, correlation_id and the link to the row in the panel.

    The user and the key come from the same dependencies as make_wallet_router (current_user_id, pix_destination — the key comes from the profile, never from the body). The e-mail goes through ManualPayoutProvider, which takes any object with EmailUtils' send(to, subject, body): in production, EmailUtils(**settings.email_kwargs()); in development, FakeEmailUtils keeps the message in outbox.

    The history the user sees in the app ("SAQUE SOLICITADO") belongs to the service. To write it in the same commit as the row, pass hooks=ManualPayoutHooks(...) to MercadoPagoWithdrawConfig: on_requested receives the session and the PENDING row inside the transaction that writes it. If it raises, nothing is written — neither the row nor the history —, no e-mail goes out and the route answers 502 WALLET_PAYOUT_REJECTED with the debit given back. hooks requires record_model: without a row there is no transaction for the callback to join, and the config refuses with ValueError. The same instance goes to ManualPayoutService for on_paid and on_rejected — see Wallet » Completing or refusing a withdrawal by hand.

    What goes wrong, and what the route answers:

    Case Answer The wallet
    nothing available (the second withdrawal included) 409 WALLET_INSUFFICIENT_BALANCE untouched
    the e-mail to the administrator failed (EmailDeliveryException, IntegrationDisabledException) 502 WALLET_PAYOUT_REJECTED; the row turns CANCELED debit given back
    the row could not be written, or on_requested raised 502 WALLET_PAYOUT_REJECTED; no e-mail debit given back
    any other error while sending 502 WALLET_PAYOUT_UNCERTAIN; the row stays PENDING debit kept, CRITICAL log
    user without a Pix key whatever your pix_destination raises untouched

    The row is written after the debit, before the e-mail

    WalletService.withdraw commits the debit before calling the provider — that is what stops two concurrent withdrawals from spending the same balance. ManualPayoutProvider writes the row right after and only then sends the e-mail; if the write fails, it refuses and the debit comes back. The only window without a row is the process dying between the debit and the write: then the ledger's WITHDRAW line, whose reference_id is the correlation_id, is what reconciles it.

    In the panel: attach the receipt and mark as paid¶

    manual_payout_admin(ManualPayoutModel, upload_storage=...) registers the table in the panel the way the job needs:

    • list filtered by status and searchable by correlation_id;
    • amount, user, key, type, correlation_id, status and who completed it are read-only; no create, delete or import;
    • receipt_key is an upload that takes PDF only: the declared type must be application/pdf and the bytes must start with %PDF- — a PNG renamed .pdf is refused with a field error, and nothing is stored;
    • the row's page has the receipt's Download link;
    • the Marcar como pago ("mark as paid") action completes only PENDING rows with a receipt, writing completed_at and completed_by (the signed-in administrator); a row without a receipt stays PENDING and the message lists its correlation_id;
    • a COMPLETED row never goes back, and its receipt can no longer be replaced (the upload is refused with a field error).

    Refusing a withdrawal gives the amount back to the wallet

    CANCELED only appears when the e-mail failed and the withdrawal itself already gave the debit back. For the administrator to refuse a PENDING row, pass ledger_factory= to manual_payout_admin: the Recusar e devolver ("refuse and refund") action turns the row REJECTED and credits the amount in a WITHDRAW_REFUND line, in the same commit — see Wallet » Completing or refusing a withdrawal by hand.

    Level 2 — signed simulation over the sandbox¶

    Mercado Pago's signature is an HMAC-SHA256 over data.id, x-request-id and ts, keyed with the webhook secret. The SDK exposes the same computation as sign_manifest, so you can produce a notification your route accepts — and test the whole path without exposing anything.

    The script creates a real Pix in the sandbox, mounts the route the way your service does, and delivers four notifications:

import os
import time
import uuid

import httpx

from tempest_fastapi_sdk import HTTPClient
from tempest_fastapi_sdk.integrations.payment import PixChargeRequest, PixPayer
from tempest_fastapi_sdk.integrations.payment.adapters import (
    MercadoPagoOrderDelivery,
    MercadoPagoPixProvider,
    make_mercado_pago_webhook_delivery_dependency,
)
from tempest_fastapi_sdk.integrations.payment.mercado_pago import (
    DEFAULT_BASE_URL,
    sign_manifest,
)

SECRET: str = os.environ.get("MERCADO_PAGO_WEBHOOK_SECRET", "local-test-secret")


def build_app(provider: MercadoPagoPixProvider) -> FastAPI:
    """Mount the webhook route exactly as the service would."""
    app = FastAPI()
    dependency = make_mercado_pago_webhook_delivery_dependency(SECRET, provider)

    @app.post("/webhooks/mercado-pago")
    async def webhook(
        delivery: MercadoPagoOrderDelivery = Depends(dependency),
    ) -> dict[str, Any]:
        """Report what the re-read decided."""
        event = provider.parse_webhook(delivery)
        return {
            "type": event.type.value,
            "status": event.charge.status.value if event.charge else None,
        }

    return app


def signed_headers(order_id: str) -> dict[str, str]:
    """Sign a notification for this order the way Mercado Pago does."""
    request_id = str(uuid.uuid4())
    ts = str(int(time.time()))
    digest = sign_manifest(
        secret=SECRET, data_id=order_id, request_id=request_id, timestamp=ts
    )
    return {"x-signature": f"ts={ts},v1={digest}", "x-request-id": request_id}


async def notify(app: FastAPI, order_id: str, headers: dict[str, str]) -> tuple[int, Any]:
    """Deliver one notification to the local route, in-process."""
    async with httpx.AsyncClient(
        transport=httpx.ASGITransport(app=app), base_url="http://local"
    ) as client:
        answer = await client.post(
            f"/webhooks/mercado-pago?data.id={order_id}&type=order",
            headers=headers,
            json={"action": "order.updated", "type": "order", "data": {"id": order_id}},
        )
    return answer.status_code, answer.json()


async def main() -> None:
    """Create a real sandbox order, then notify the local route about it."""
    token: str = os.environ["MERCADO_PAGO_TEST_SELLER_ACCESS_TOKEN"]
    async with HTTPClient(
        base_url=DEFAULT_BASE_URL,
        default_headers={"Authorization": f"Bearer {token}"},
    ) as http:
        provider = MercadoPagoPixProvider(http)
        charge = await provider.create_pix_charge(
            PixChargeRequest(
                amount_cents=1990, reference="webhook-test-1", payer=PixPayer(email="buyer@example.com")
            )
        )
        app = build_app(provider)
        order_id = charge.provider_charge_id

        print("pending   ", await notify(app, order_id, signed_headers(order_id)))
        await provider.cancel_pix_charge(order_id)
        print("cancelled ", await notify(app, order_id, signed_headers(order_id)))
        print("forged    ", await notify(app, order_id, {"x-signature": "ts=1,v1=00", "x-request-id": "x"}))
        print("simulated ", await notify(app, "ORD00000000000000000000000000", signed_headers("ORD00000000000000000000000000")))

    Recap¶

    • A notification only says which order changed; the route re-reads to learn what.
    • FakeMercadoPagoOrdersAPI plus the real adapter test payment, refund, cancellation and expiry with no network; tempest mercado-pago fake-api and simulate-webhook do the same with the service running.
    • make_mercado_pago_router mounts the webhook route; with simulate=True (development/test only), the front end pays and refunds through the /dev/mercado-pago/... routes, which deliver the webhook to the real route; with withdraw=, a withdrawal empties the wallet and becomes a manual Pix the administrator completes in the panel, with the PDF receipt.
    • A service with its own webhook route mounts only the simulation routes with make_mercado_pago_simulation_router(webhook_route=...); MercadoPagoSimulator moves, signs and delivers from a script, and mercado_pago_simulation_actions puts "Simular pagamento" in the panel.
    • sign_manifest produces a notification your route accepts: test the whole path without a public URL.
    • A wrong signature is 401 before any call; an unknown id is 200 with no charge, because answering an error would make Mercado Pago resend — that is what the provider's documentation describes; the redelivery was not observed here.
    • For the dashboard and a real delivery, a tunnel (cloudflared, ngrok) gives the public URL.
