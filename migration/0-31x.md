# Migração 0.31x

Use ao atualizar a partir de uma versão anterior a estas releases: 0.319.0, 0.318.0, 0.316.0, 0.314.0, 0.313.0, 0.312.0 e 0.311.0.

Parte do [Guia de migração](https://mauriciobenjamin700.github.io/tempest-fastapi-sdk/migration.md).

## 0.319.0 — contagem do `bulk_create_values` e do `bulk_upsert`

`bulk_create_values` e `bulk_upsert` (modo `"update"`) devolvem `0` quando o
banco informa `0`; até a 0.318.x um `rowcount` zero virava `len(rows)`.
`bulk_upsert(update_columns=[])` levanta `ValueError` apontando para
`on_conflict="nothing"`.

### O que fazer

- Código que tratava o retorno como "sempre o tamanho do lote" passa a
  receber o número real.
- Para inserir ignorando o que já existe, use
  `bulk_upsert(..., on_conflict="nothing")` (ou `returning_ids=True` para
  saber quais linhas foram criadas).

## 0.318.0 — leitores de log, `log_dir` vazio, IP do header e login do `/admin`

Quatro mudanças de comportamento sem troca de assinatura.

1. **Leitores de log leem os backups.** `GET /logs`, `/admin/logs` e
   `read_log_entries` passam a ler também os arquivos rotacionados
   (`info.log.1`, `info.log.2026-10-20`), e o `total` soma os backups. O
   `DELETE /logs` continua só truncando o arquivo corrente; para apagar os
   backups, `DELETE /logs?delete_backups=true` (ou
   `clear_log_files(..., delete_backups=True)`).
2. **`log_dir` vazio é erro.** `make_logs_router(log_dir="")`,
   `clear_log_files("")` e `resolve_log_files("")` levantam `ValueError`; antes
   `Path("")` resolvia para o diretório corrente. `read_log_entries("")`
   devolve vazio. Quem passa `settings.LOG_DIR` com o log em arquivo desligado
   não monta o router de logs.
3. **O header de IP confiável precisa ser um IP.** `get_client_ip` e
   `get_client_ip_from_scope` validam o valor com `ipaddress`; o que não é IP
   cai no endereço da conexão. Afeta rate limit, throttles de login e
   auditoria. O proxy de borda precisa **sobrescrever** o header, não
   acrescentar a ele.
4. **`/admin/login` tem limite de tentativas.** 5 falhas por identificador a
   cada 900 s, por padrão, em memória; o limite por IP (20 / 900 s) só liga com
   `trusted_ip_header`. Com mais de um processo, passe `login_throttle=` /
   `login_ip_throttle=` sobre o Redis; `False` desliga.

### O que fazer

- Painel ou script que conta linhas de `/logs` espera números maiores.
- Troque `make_logs_router(log_dir=settings.LOG_DIR)` por uma montagem
  condicional quando `LOG_DIR` pode ser vazio.
- Confira que o proxy grava o IP real no header configurado.

## 0.316.0 — `set-password` pede o fator em conta com MFA

`tempest user set-password` numa conta com MFA ativo (e `AUTH_MFA_ENABLED=True`)
passa a pedir o código — TOTP ou recovery code — e troca a senha por
`UserAuthService.change_password_with_mfa`. Sem código válido em três
tentativas, o comando sai com código 1 e a senha não muda. Até a 0.315.x o
comando trocava a senha sem pedir o fator.

### O que fazer

1. Script ou CI que roda `set-password` sem terminal numa conta com MFA deixa
   de funcionar: não há quem digite o código.
2. Para recuperar quem perdeu o celular **e** os recovery codes, rode
   `tempest user mfa-reset --email <e>` (`--yes` fora de terminal) e depois
   `set-password`. Veja [a receita de MFA](https://mauriciobenjamin700.github.io/tempest-fastapi-sdk/recipes/mfa.md#mfa-reset).
3. Para aceitar recovery code, o comando precisa da tabela de recovery codes
   (`--recovery-code-model`, default `src.db.models:UserRecoveryCodeModel`).

## 0.316.0 — o segundo item do `UserAuthService.signup` pode ser `ActivationWithheld`

A tupla devolvida por `signup` passa a ter três formas no segundo item:
`None` (a conta nasceu ativa), `ActivationToken` (o link foi emitido) e o novo
`ActivationWithheld(user_id)` (o link foi retido). O terceiro só sai com
`AUTH_AUTO_ACTIVATE=false` **e** `UserAuthService(refuses_email_link=...)`
recusando a conta nova; sem o predicado, o comportamento em runtime é o de
antes. O router do SDK já trata o tipo novo.

### O que fazer

1. Se você chama `signup` direto e lê `.url` ou `.token` do segundo item,
   teste `isinstance(activation, ActivationToken)` antes: com
   `ActivationWithheld` a conta existe, inativa e sem link. O mypy acusa
   `union-attr` onde isso falta.
2. Só `None` autoriza emitir o par de JWT logo após o cadastro.
3. Se você sobrescreve `signup` e repassa ao `super()`, ajuste a anotação de
   retorno.

## 0.314.0 — Python 3.12 passa a ser o mínimo

O SDK deixa de suportar Python 3.11. O `requires-python` sobe para `>=3.12`, e
as versões suportadas passam a ser **3.12, 3.13 e 3.14**.

Quem está em 3.11 **fica na 0.313.x**: o instalador descarta as releases cujo
`requires-python` exclui o interpretador. Pedir a versão nova num ambiente 3.11
falha antes de instalar qualquer coisa. Medido com o `uv`:

```text
error: The requested interpreter resolved to Python 3.11.12, which is incompatible with the project's Python requirement: `>=3.12` (from `project.requires-python`)
```

### O que fazer

1. Suba o interpretador do serviço para 3.12 ou mais novo
   (`uv python pin 3.13`, a imagem base do `Dockerfile`, o runtime da CI).
2. Ajuste o `requires-python` do seu `pyproject.toml` para `>=3.12`. O
   `tempest new` já gera assim, com `target-version = "py312"` no ruff e
   `python_version = "3.12"` no mypy.
3. Rode `uv lock` e `uv sync`. Com o piso novo o lock deixa de carregar o
   split do 3.11: no lock do próprio SDK saíram `tomli`, `async-timeout` e
   `audioread`, e `numpy`, `scipy` e `librosa` passaram a ter uma versão só.

Para continuar em 3.11 por enquanto, fixe a faixa:
`uv add "tempest-fastapi-sdk>=0.313.0,<0.314.0"`.

## 0.314.0 — login social de conta com TOTP pede o segundo fator

`GET /auth/oauth/{provider}/callback` e `POST /auth/oauth/{provider}/token`
passam a espelhar o `/auth/login`. Quando a conta resolvida tem TOTP inscrito
(e `AUTH_MFA_ENABLED=True`), a resposta **não traz o par nem cookie de
sessão**: traz `mfa_required=true` + `mfa_token`, e o par só sai do
`/auth/mfa/verify`, com `amr == ["ext", "otp"]`. Até a 0.313.x o provedor
bastava, e a conta pulava o fator que tinha inscrito.

### O que fazer

1. No cliente do login social, trate o desafio como no login por senha: se
   `mfa_required` for `true`, peça o código e faça
   `POST /auth/mfa/verify` com o `mfa_token`. Conta sem MFA não muda — o par
   continua na própria resposta, com `amr == ["ext"]`.
2. Se você sobrescreve `UserAuthService.login_with_oauth`, mova a lógica para
   o novo `authenticate_oauth` (resolve a conta sem emitir nada). As rotas não
   chamam mais `login_with_oauth`, e o router loga um aviso ao ser montado
   quando acha o override. Chamar `login_with_oauth` direto continua emitindo
   o par sem perguntar pela MFA.
3. Se você sobrescreve `issue_mfa_token`, aceite o novo
   `amr: Sequence[str] | None = PASSWORD_AMR` e repasse ao `super()`. Sem ele
   o token sai sem o primeiro passo, e o `/auth/mfa/verify` volta ao
   `["pwd", "otp"]` de antes — o router também avisa no log.

## 0.314.0 — ativação e reset por link carimbam `amr=["email"]`

O par que `POST /auth/activate/{token}` e `POST /auth/password-reset/confirm`
emitem para conta **sem** MFA passa a sair com `amr == ["email"]`
(`AMR_EMAIL_LINK`), não mais `["pwd"]`: nenhum dos dois confere senha. Com
TOTP inscrito, o `/auth/mfa/verify` desse desafio emite `["email", "otp"]`. O
`refresh` repete o `amr` da origem, então a sessão continua `["email"]` depois
de rotacionar.

### O que fazer

- Código que lê `"pwd" in amr` como "esta sessão começou num login" passa a
  ver `"email"` nesses dois caminhos. Se a sua regra é "qualquer sessão de um
  fator", compare com `AMR_EMAIL_LINK` também; se é "a senha foi conferida",
  a mudança é a correção que você queria.
- `make_mfa_required_dependency` não muda: `email` não está em
  `MFA_AMR_METHODS`, e o gate recusa o par como recusava o `["pwd"]`.
- Override de `issue_token_pair` sem `amr=` continua sendo chamado sem a
  keyword, e o par sai com o default do override (`["pwd"]`, se delega ao
  `super()`), como antes.

## 0.313.0 — classe terminada em `Enum` não dobra mais o sufixo do tipo

`enum_type_name` tira um `Enum` do fim do nome da classe antes de acrescentar
`_enum`. Só muda quem tem enum com esse sufixo:

| Classe | Antes | Agora |
| --- | --- | --- |
| `CandidateSlugEnum` | `candidate_slug_enum_enum` | `candidate_slug_enum` |
| `OrderStatus` | `order_status_enum` | `order_status_enum` (igual) |

O banco continua com o nome antigo até uma migration renomear o tipo, e no
PostgreSQL o model passa a escrever o nome novo em todo `INSERT`, `UPDATE` e
`WHERE` com a coluna. Medido no PostgreSQL 16 com asyncpg, antes da migration:
`type "candidate_slug_enum" does not exist` nos três.

### O que fazer

1. Atualize o SDK e rode `tempest db revision --autogenerate -m "renomeia tipos de enum"`.
   O `sync_enum_types` detecta o tipo renomeado (no PostgreSQL pelo
   `information_schema`, no SQLite pelo nome do `CHECK`) e escreve um
   `op.rename_enum_type` por tipo, com o reverso no `downgrade`:

    ```python
    from alembic import op

    from tempest_fastapi_sdk.db.enum_migrations import EnumColumnRef


    def upgrade() -> None:
        """Renomeia o tipo do enum para o nome sem o sufixo dobrado."""
        op.rename_enum_type(
            "candidate_slug_enum_enum",
            "candidate_slug_enum",
            columns=[EnumColumnRef(table="candidates", column="slug")],
        )
    ```

2. Aplique a migration **antes** de o código novo atender tráfego (o `alembic
   upgrade head` do deploy já faz isso). `tempest db check` falha enquanto a
   migration não existir, então a CI pega o esquecimento.

Para manter o nome antigo numa coluna, passe-o explícito:
`mapped_column(TempestEnum(CandidateSlugEnum, name="candidate_slug_enum_enum"))`.

## 0.313.0 — o 429 do auth tem código próprio

Os três limites do `make_auth_router` deixam de responder o `code` genérico
`TOO_MANY_REQUESTS`, o mesmo de qualquer outro 429 do app:

| Refuso | Antes | Agora |
| --- | --- | --- |
| login acima do limite, por e-mail **ou** por cliente | `TOO_MANY_REQUESTS` | `LOGIN_THROTTLED` (`LoginThrottledException`) |
| signup acima do limite | `TOO_MANY_REQUESTS` | `SIGNUP_THROTTLED` (`SignupThrottledException`) |
| código MFA errado acima do limite | `TOO_MANY_REQUESTS` | `MFA_THROTTLED` (`MfaThrottledException`) |

O status continua `429`, com `Retry-After` e `details.retry_after_seconds`. As
três classes herdam de `TooManyRequestsException`, então `except
TooManyRequestsException` continua pegando. Muda para quem compara o `code`:
troque `code == "TOO_MANY_REQUESTS"` pelo código do fluxo. Com
`default_message_catalog()`, o `detail` passa a ser uma mensagem específica
(`Muitas tentativas de login. Aguarde um pouco e tente de novo`) em vez de
`Requisições em excesso`.

## 0.313.0 — refresh token guarda o `amr`, e `/mfa/confirm` responde `200`

O access token passou a carregar o claim `amr` (como a sessão foi autenticada),
e o `BaseUserRefreshTokenModel` ganhou a coluna `amr` (texto, nullable) para o
`refresh` repetir esse valor. Como a coluna é mapeada no modelo base, **migre
o banco antes de atualizar o pacote** se você usa `refresh_token_model`: sem
ela, toda emissão de par falha — medido com SQLite, `POST /auth/signup` com
ativação automática respondeu `500` (`OperationalError`). Quem não passa
`refresh_token_model` não muda nada no banco.

### O que fazer

1. Gere a migration (`uv run tempest db revision -m "refresh token amr"`, ou
   `alembic revision --autogenerate`) ou escreva-a à mão, com o nome da sua
   tabela:

    ```python
    import sqlalchemy as sa
    from alembic import op

    revision: str = "0313_refresh_token_amr"
    down_revision: str | None = "<a revisão anterior>"


    def upgrade() -> None:
        """Adiciona o amr da família de refresh token."""
        op.add_column(
            "user_refresh_tokens",
            sa.Column("amr", sa.String(length=64), nullable=True),
        )


    def downgrade() -> None:
        """Remove o amr da família de refresh token."""
        op.drop_column("user_refresh_tokens", "amr")
    ```

2. Rode `uv run tempest db upgrade` (ou `alembic upgrade head`) e só então faça
   o deploy da versão nova.

Linhas antigas ficam com `NULL`: o `refresh` delas emite access token **sem**
`amr`, que `make_mfa_required_dependency` trata como "sem segundo fator".

Duas mudanças de comportamento vêm junto:

- **`POST /auth/mfa/confirm` responde `200` com um `LoginResponseSchema`**, não
  mais `204`. Confirmar revoga todos os refresh tokens do usuário, e o par novo
  no corpo (ou nos cookies, no modo cookie) é o que mantém o dispositivo
  logado. Cliente que confere `status === 204` passa a checar `200` e guarda o
  par novo.
- **`mfa_confirm` revoga as sessões por padrão.** Quem chama o serviço direto e
  precisa manter as sessões passa `revoke_sessions=False`.

### O reset de senha e a reativação por link pedem o segundo fator

`POST /auth/password-reset/confirm` e `POST /auth/activate/{token}` passam a
espelhar o `/auth/login`: quando a conta tem TOTP inscrito, não devolvem o par
— devolvem `mfa_required=true` + `mfa_token`, e o par só sai do
`/auth/mfa/verify`, com `amr` de MFA. A senha é trocada de todo jeito.

Cliente que chamava o `confirm` (ou o `activate` de uma conta reativada) e
guardava `access_token` direto precisa tratar o desafio: se `mfa_required` for
`true`, peça o código e faça o `/auth/mfa/verify`. Conta sem MFA não muda —
continua recebendo o par na própria resposta. Ativar uma conta recém-cadastrada
também não muda: ela nunca tem fator.

`ActivationResponseSchema` ganhou `mfa_required` / `mfa_token`, e
`access_token` / `refresh_token` passaram a ser opcionais (`str | None`), como
no `LoginResponseSchema`. Quem lê o par de uma ativação de conta nova não muda
nada.

O reset de senha agora **revoga as sessões já abertas** na mesma transação que
grava o hash, como o `/auth/mfa/confirm` e o `tempest user set-password` já
faziam: um refresh token DB-backed emitido antes do reset deixa de trocar por
par novo (responde 401). Access tokens já emitidos ainda valem até o TTL. Quem
chamava `UserAuthService.confirm_password_reset` e precisa manter as sessões
passa `revoke_sessions=False` — assinatura antiga de override continua sendo
chamada pelo router, e delega para o default que revoga. Refresh token
stateless (sem `refresh_token_model`) não tem linha a revogar e segue valendo
até expirar.

## 0.312.0 — Mercado Pago: Pix vencido e busca de chargebacks

Duas mudanças de comportamento, as duas medidas no sandbox em 2026-10-10.

**Pix vencido agora é `EXPIRED`.** Uma order que o Mercado Pago devolve
`canceled` / `expired` passou a ser `PaymentStatus.EXPIRED`, e o webhook a
entrega como `PixEventType.CHARGE_EXPIRED`. Até a 0.311.0 ela saía
`CANCELLED` / `CHARGE_CANCELLED`. Se o seu serviço tratava o vencimento no
ramo de cancelamento, trate os dois:

```python
from tempest_fastapi_sdk.integrations.payment import PaymentStatusEnum, PixCharge


def is_closed_unpaid(charge: PixCharge) -> bool:
    """Tell whether a Pix charge ended without being paid."""
    return charge.status in {PaymentStatusEnum.CANCELLED, PaymentStatusEnum.EXPIRED}
```

**`search_chargebacks` exige `payment_id`.** A busca respondia `400` sem esse
filtro, inclusive na única forma que o método aceitava (`limit` / `offset`),
então ela nunca funcionava. Agora:

| Antes | Agora |
| --- | --- |
| `await client.search_chargebacks(limit=10)` → sempre `400` | `await client.search_chargebacks(payment_id="123")` → `ChargebackSearchResponse` |
| `dict[str, Any]` | `found.paging.total`, `found.results` (itens ainda `dict[str, Any]`) |

## 0.311.0 — Mercado Pago: a API de Payments saiu do SDK

O painel do Mercado Pago marca a API de Payments (`/v1/payments`) como
*"Esta API será descontinuada em breve"*, e o SDK passou a cobrar pela API de
Orders. Quem usava o caminho de Payments troca assim:

| Antes | Agora |
| --- | --- |
| `client.create_payment(body=PaymentRequest(...))` com Pix | `MercadoPagoPixProvider(http).create_pix_charge(PixChargeRequest(...))` |
| `client.create_payment(...)` com `token` de cartão | `MercadoPagoCardProvider(http).create_card_charge(CardChargeRequest(...))` |
| `create_pix_payment` / `get_pix_payment` / `parse_pix_payment` | `create_pix_charge` / `get_pix_charge` — o QR vem em `PixCharge.br_code` e `qr_code_base64` |
| `client.get_payment(id)` | `get_pix_charge(order_id)` / `get_card_charge(order_id)`, ou `client.get_order(order_id)` |
| `client.update_payment(id, body={"capture": True})` | `capture_card_charge(order_id)` |
| `client.update_payment(id, body={"status": "cancelled"})` | `cancel_pix_charge(order_id)` / `cancel_card_charge(order_id)` |
| `client.create_refund(id, ...)` | `refund_card_charge(order_id, amount_cents=...)` |
| `PixPayment`, `Payment` | `PixCharge`, `CardCharge`, ou o `Order` gerado |
| as 7 operações de QR presencial V1/V2 e QR dinâmico antigo | sem substituto neste SDK: a própria spec as marca `deprecated`, e a API de Orders da spec só declara `type: online` |

**Removidos sem substituto direto** (o equivalente, quando existe, é o
`Order` gerado ou os contratos `PixCharge` / `CardCharge`):

- **Métodos de `MercadoPagoClient`:** `create_payment`, `search_payments`,
  `get_payment`, `update_payment`, `cancel_payment`, `create_refund`,
  `list_refunds`, `get_refund`, e os 7 de QR presencial —
  `create_instore_order_v1`, `delete_instore_order_v1`,
  `create_instore_order_v2`, `get_instore_order_v2`,
  `delete_instore_order_v2`, `create_dynamic_qr_order`,
  `create_qr_tramma_dynamic`.
- **Funções e constantes:** `create_pix_payment`, `get_pix_payment`,
  `parse_pix_payment`, `PAYMENTS_PATH`.
- **Modelos e enums:** `PixPayment`, `PixPointOfInteraction`,
  `PixTransactionData`, `Payment`, `PaymentRequest`, `PaymentPayer`,
  `PaymentPayer2`, `PaymentCard`, `PaymentCardCardholder`, `PaymentItem`,
  `PaymentAdditionalInfo`, `PaymentAdditionalInfoPayer`,
  `PaymentAdditionalInfoShipments`, `PaymentTransactionDetails`,
  `PaymentOperationType`, `PaymentPaymentTypeId`, `PaymentProcessingMode`,
  `PaymentSearchResult`, `SearchPaymentsRange`, `PaymentUpdateRequest`,
  `PaymentUpdateRequestStatus`, `CancelPaymentBody`, `RefundRequest`,
  `CreateRefundResponse`, `CreateRefundResponseSource`, `GetRefundResponse`,
  `GetRefundResponseSource`, `ListRefundsResponse`,
  `ListRefundsResponseSource` e `PaymentStatus` de `mercado_pago`.
  O `PaymentStatus` **canônico**, de `integrations.payment`, continua — é o
  que os contratos usam.

**Tipos que mudaram:**

- `Order.status`, `Order.status_detail`, `OrderTransactionPayment.status` e
  `OrderTransactionPayment.status_detail` passam de enum para `Enum | str`:
  o sandbox devolveu valores fora da lista. Um `match` exaustivo sobre o enum
  precisa de um ramo para a string.
- `get_authenticated_user()` devolve `AuthenticatedUser` em vez de
  `dict[str, Any]`: troque `user["id"]` por `user.id` (o que não foi
  declarado está em `user.model_extra`).
- Dois enums ganharam nome próprio: `ListPaymentMethodsResponseItemProcessingModesItem`
  (processing mode de `list_payment_methods`) e `UpdateAdvancedPaymentBodyStatus`
  (status do corpo de `update_advanced_payment`).

Três diferenças que pedem ajuste além do nome:

1. **O id muda de forma.** Uma order tem id de texto (`ORD…`), não número.
   Se você guardava o id do pagamento como inteiro, a coluna vira texto.
2. **O webhook muda de recurso.** A notificação deve passar a apontar para a
   order — é o que o documento do provedor descreve (ações `order.created` /
   `order.updated`); a entrega real observada em 2026-11-13 trazia
   `type=order`, e `event.event` é `ORDER` desde a v0.358.0.
   Troque a leitura manual de `data.id` por
   `make_mercado_pago_webhook_delivery_dependency`, e marque o evento de
   Order na configuração de webhooks da aplicação.
3. **A credencial precisa ser de uma aplicação "API de Orders".** Medido: a
   aplicação Checkout Pro de uma conta vendedora de teste responde `401
   Unauthorized use of live credentials` a cobrança direta. A receita
   [contas e credenciais de teste](https://mauriciobenjamin700.github.io/tempest-fastapi-sdk/recipes/mercado-pago-sandbox.md) mostra o
   caminho.
