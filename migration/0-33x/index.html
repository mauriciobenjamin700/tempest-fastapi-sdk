    Migração 0.33x¶

    Use ao atualizar a partir de uma versão anterior a estas releases: 0.336.0, 0.335.0, 0.332.0, 0.331.0 e 0.330.0.

    Parte do Guia de migração.

    0.336.0 — correções de segurança (tempo real)¶

    Onde O que muda O que fazer
    SSEBroker com Redis Com o channel_prefix default "sse", a construção registra um WARNING: o pub/sub do Redis ignora o índice de DB, e outro serviço na mesma instância com o mesmo prefixo troca eventos com este Passe um channel_prefix próprio do serviço ("orders-api:sse") em todo worker ao mesmo tempo — workers com prefixos diferentes não se enxergam
    Inscrição Web Push (WebPushSubscriptionService.subscribe, make_web_push_router, registro web do make_push_router) Endpoint que é ou resolve para endereço não público responde 422 PUSH_ENDPOINT_NOT_PUBLIC e não é gravado; o send_many devolve para poda o endpoint gravado antes que não é https ou é IP literal não público Nada, se o push service é público. Push service próprio na rede interna: allow_private_networks=True no WebPushDispatcher abre inscrição e envio juntos

    0.336.0 — password-change devolve um par novo, set-password apaga passkeys¶

    Onde O que muda O que fazer
    POST /auth/password-change Responde 200 com LoginResponseSchema em vez de 204 sem corpo, e o corpo aceita code opcional. Conta sem MFA: par novo, emitido depois da revogação de todas as sessões (em cookies para quem se autenticou pelo cookie de acesso). Conta com MFA sem code: a senha muda e a resposta é o desafio do login (mfa_required: true, mfa_token), sem par. Com code válido: par com amr de MFA; code errado: 401 e nada muda Cliente bearer: guarde o par da resposta e descarte o antigo; numa conta com MFA, mande o code junto ou trate o mfa_required como no login. Cliente que tratava qualquer 2xx como sucesso não quebra, mas continua deslogando no fim do TTL do access token se não guardar o par
    tempest user set-password Apaga as passkeys WebAuthn do usuário na mesma transação, quando acha a tabela (--webauthn-credential-model, default src.db.models:UserWebAuthnCredentialModel) --keep-passkeys mantém o comportamento antigo; avise o usuário que ele cadastra a passkey de novo
    signup(fields=...) e signup_schema totp_secret, totp_enabled_at, totp_last_step e toda coluna de __secret_columns__ do user model são recusados (ValueError no service, descartados pela rota) Nada para as colunas do MFA, que só o fluxo de inscrição grava. Se o seu cadastro grava uma coluna própria de __secret_columns__, mova a escrita para o on_signup
    IntrospectionAuth Novo audiences=; sem ele, um WARNING por instância na construção Passe audiences= com o client id do serviço no provedor. Veja Amarrar o token a este serviço

    0.336.0 — CORS, storage, busca textual e Stripe¶

    Onde O que muda O que fazer
    CORSSettings com ENV=production Com CORS_ALLOW_CREDENTIALS=true, "null" em CORS_ORIGINS ou um CORS_ORIGIN_REGEX que casa com uma origem .invalid (.*, https://.*) impedem o boot, como "*" já impedia Liste as origens do frontend em CORS_ORIGINS, ou ancore o regex no seu domínio
    accel_redirect_response, serve_object(accel_redirect=True) media_type fora de tipo/subtipo (parâmetro, vírgula, CR/LF) levanta ValueError, como no presigned_get_url; text/plain; charset=utf-8 deixa de ser aceito nesse caminho Passe o tipo sem parâmetros (text/plain)
    Busca textual (search, search_condition, full_text_search) hashed_password e as colunas de __secret_columns__ respondem 422; a mensagem passa a ser ... has no searchable column ..., e details["allowed"] só aparece quando o repositório declara searchable_columns Se a busca recebe o campo da requisição, declare searchable_columns no repositório
    StripeClient create, retrieve, update e delete levantam StripeObjectMismatchError quando o object da resposta não é o do recurso Trate a exceção onde hoje trata StripeError (é subclasse dela)
    ps_single_quote (hostbridge) Dobra também as aspas tipográficas U+2018–U+201B Nada

    0.335.0 — BaseUserModel ganha a coluna email_verified_at¶

    O BaseUserModel passou a mapear email_verified_at (timestamp com fuso, nullable): quando o dono da conta provou que lê o endereço atual. Como a coluna é mapeada na base, migre o banco antes de atualizar o pacote: sem ela, toda consulta ao user model falha (no such column: users.email_verified_at, medido com SQLite).

    A mudança de comportamento: a ligação de login social por e-mail (AUTH_OAUTH_LINK_BY_VERIFIED_EMAIL=true) passa a exigir a coluna preenchida. Conta antiga fica com NULL, então deixa de ser ligada por e-mail (409 OAUTH_EMAIL_TAKEN) até provar o endereço — por POST /auth/email-verify/request e o link que chega na caixa de entrada. Serviço com o knob desligado (o default) não muda nada além da migration. O que preenche e o que limpa a coluna está em O que conta como e-mail verificado.

    O que fazer¶

    1. Gere a migration (uv run tempest db revision -m "email verified at", ou alembic revision --autogenerate) ou escreva-a à mão:

      import sqlalchemy as sa
from alembic import op

revision: str = "email_verified_at"
down_revision: str | None = "<a revisão anterior>"


def upgrade() -> None:
    """Adiciona a prova de posse do e-mail."""
    op.add_column(
        "users",
        sa.Column("email_verified_at", sa.TIMESTAMP(timezone=True), nullable=True),
    )


def downgrade() -> None:
    """Remove a prova de posse do e-mail."""
    op.drop_column("users", "email_verified_at")

    2. Rode uv run tempest db upgrade (ou alembic upgrade head) e só então faça o deploy da versão nova.

    Preencher as contas antigas — decisão sua¶

    O SDK não preenche nada por você: ele não sabe como cada conta antiga ficou ativa. Preencha só se você sabe que as contas ativas do banco foram ativadas pelo link enviado por e-mail — ou seja, que o serviço sempre rodou com AUTH_AUTO_ACTIVATE=false, AUTH_RETURN_TOKEN_IN_RESPONSE=false e EmailUtils ligado, e que ninguém ativou conta pelo admin ou por tempest user activate. Se qualquer uma dessas falhou para parte do banco, restrinja o WHERE a essa parte (por created_at, por exemplo) ou não preencha.

    Não existe coluna com o momento da ativação; created_at é o limite inferior que o banco conhece, e é o valor que o passo abaixo grava. Acrescente ao upgrade() da migration:

    import sqlalchemy as sa
from alembic import op


def upgrade() -> None:
    """Marca como verificadas as contas ativas, que foram ativadas por e-mail."""
    users = sa.table(
        "users",
        sa.column("is_active", sa.Boolean()),
        sa.column("created_at", sa.TIMESTAMP(timezone=True)),
        sa.column("email_verified_at", sa.TIMESTAMP(timezone=True)),
    )
    op.execute(
        users.update()
        .where(users.c.is_active.is_(True), users.c.email_verified_at.is_(None))
        .values(email_verified_at=users.c.created_at)
    )

    Sem esse passo, a conta que quiser ligar o login social por e-mail verifica o endereço uma vez, e a ligação volta a funcionar.

    0.335.0 — correções de segurança que mudam comportamento¶

    Esta release fecha vulnerabilidades, e várias correções trocam um default inseguro por um seguro. A tabela diz o que muda para quem já usa o SDK e o que fazer. O detalhe de cada item está no CHANGELOG e na receita citada.

    Onde O que muda O que fazer
    ENV=production AUTH_AUTO_ACTIVATE=true ou AUTH_RETURN_TOKEN_IN_RESPONSE=true impedem o boot; sem EmailUtils no UserAuthService (com um auth_settings que compõe EnvironmentSettings), os fluxos que mandam link respondem 503 INTEGRATION_DISABLED Desligue as duas flags em produção e passe email= ao service
    key_by_header is_known= passa a ser obrigatório; sem ele, TypeError Passe um verificador síncrono que diga se o valor do header é uma chave que você emitiu
    IdempotencyMiddleware Requisição sem credencial não é deduplicada; entrada gravada por versão antiga responde 422 IDEMPOTENCY_KEY_REUSED até expirar Passe allow_anonymous=True só se precisar deduplicar POST anônimo; espere o TTL das entradas antigas
    WebhookSignatureVerifier, make_stripe_webhook_dependency Segredo vazio levanta ValueError na construção Configure o segredo do webhook antes de subir
    POST /auth/webauthn/register/begin Exige corpo WebAuthnRegisterBeginSchema (current_password e, com MFA, code); sem corpo, 422 Atualize o cliente para pedir a senha antes de cadastrar a passkey
    Reset de senha e mfa_reset Apagam as passkeys do usuário revoke_passkeys=False mantém o comportamento antigo; avise os usuários que eles cadastram a passkey de novo
    make_admin_router com access_policy Console SQL, tasks e logs ficam negados a todos Passe surface_policy= liberando quem deve vê-los
    Admin Colunas de credencial do SDK (totp_secret, chaves de push, digests de token) somem das telas, inclusive de list_display; cookies emitidos antes da atualização são recusados uma vez Nada; os operadores fazem login de novo
    SessionStore próprio O protocolo ganhou touch; store sem ele funciona com DeprecationWarning Implemente touch, que atualiza só sessão que ainda existe
    TaskQueue (resultados) Resultado gravado em JSON; resultado em pickle de antes da atualização fica ilegível até o TTL result_serializer="pickle" só para Redis que ninguém mais escreve
    WebPushDispatcher Endpoint que resolve para rede interna não é entregue; o envio tem timeout de 10 s allow_private_networks=True só em ambiente de teste; atrás de proxy sem DNS externo, passe resolver=
    describe_image_tool, transcribe_audio_tool O argumento path só existe com path_root= Passe path_root= com a pasta que o modelo pode ler
    ChatMemory.delete_for_chat Exige user_id Passe o dono do chat
    HoneypotMiddleware patterns= casa só com o path; a query tem query_patterns= Mova padrões de query para query_patterns=
    STT, diarização, voiceprint Áudio acima de 1 h decodificada é recusado (422) max_audio_seconds=None para arquivos confiáveis e longos
    Login por WebSocket Use make_jwt_bearer_resolver, que confere o tipo do token Troque o resolver escrito à mão

    0.332.0 — DLQ fixa a política de ack do consumidor¶

    Num QueueSpec com dead-letter, o MessageBroker.on / register e o subscribe / Consumer fixam REJECT_ON_ERROR no próprio assinante quando ack_policy fica None (#642). Passar ACK, ACK_FIRST ou NACK_ON_ERROR num spec com dead-letter agora levanta ValueError no registro: nenhuma das três manda a falha para a DLQ. Consumidor sem dead-letter não muda.

    O que fazer¶

    1. Tire o ack_policy=AckPolicy.REJECT_ON_ERROR dos consumidores com DLQ, se quiser: o default já é esse. Mantê-lo continua valendo.
    2. Consumidor com dead-letter que passava ACK, ACK_FIRST ou NACK_ON_ERROR falha no boot: troque por REJECT_ON_ERROR (ou omita), ou tire o dead-letter do spec se a falha não deve ir para a DLQ.

    0.331.0 — visual novo do admin, upload com teto no storage¶

    O admin.css foi reescrito sobre tokens e o AdminTheme mudou dois defaults: header_bg passa de "#0f172a" para "#ffffff" e radius de "6px" para "8px". As classes tempest-admin-* continuam.

    O protocolo SubjectStorageClient ganhou presigned_post_policy, e presigned_get_url ganhou filename, media_type e as_attachment.

    A busca da lista do admin (?q=) passa a procurar por trecho em qualquer search_fields; antes comparava por igualdade em todos.

    O que fazer¶

    1. Quem passa custom_css_url sobrescrevendo cores fixas do header escuro: revise a folha contra o header claro.
    2. Para manter o header escuro, passe AdminTheme(header_bg="#0f172a"): o texto do chrome passa a claro sozinho pela luminância. Se o palpite errar, fixe com header_fg=.
    3. Atrás de um proxy que termina o TLS, aproveite o upgrade para declarar SERVER_PUBLIC_SCHEME=https e registrar o PublicSchemeMiddleware (Segurança): sem isso o login do admin aparece como não seguro.
    4. Um cliente de storage seu que implemente SubjectStorageClient precisa de presigned_post_policy e dos três parâmetros novos de presigned_get_url para continuar passando no type-checker. AsyncMinIOClient, LocalObjectStorageClient e FakeObjectStorageClient já cumprem.
    5. Serviço que gera cliente a partir do OpenAPI e usa image_media_type_field: chame prune_orphan_enum_schemas(app) no create_app para tirar o ImageMediaType órfão (Uploads).

    0.330.0 — inscrição de push não muda mais de dono¶

    POST /subscribe (Web Push) e POST /register (push mobile) não transferem mais para quem chamou um endpoint/token já registrado por outra conta (#632): a linha fica com o dono e a rota responde igual a uma inscrição nova. Antes, o login de outra conta no mesmo navegador ou aparelho movia a inscrição sozinho.

    O que fazer¶

    1. No cliente, chame POST /unsubscribe (Web Push) ou POST /unregister (mobile) no logout, antes de outra conta entrar no mesmo dispositivo.
    2. Se mover dispositivos entre contas é um caso real do seu serviço, ligue explicitamente: make_web_push_router(..., transfer_ownership=True) / make_push_router(..., transfer_ownership=True), ou subscribe(..., transfer_ownership=True) / register(..., transfer_ownership=True) no service.
    3. Override de subscribe/register não precisa mudar: o router só passa transfer_ownership quando a opção está ligada.
