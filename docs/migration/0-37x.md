# Migração 0.37x

Use ao atualizar a partir de uma versão anterior a estas releases: 0.374.0, 0.373.0 e 0.372.0.

Parte do [Guia de migração](../migration.md).

## 0.374.0 — `Agent` e `AIChatPipeline` rodam chamada de ferramenta escrita no texto

Antes, uma resposta do modelo com `tool_calls` vazio era sempre a resposta final, mesmo quando o `content` era exatamente uma chamada em JSON (`{"name": "buscar_pedido", "arguments": {"pedido_id": "PED-1042"}}`). Agora, por padrão, o `Agent` e o loop de ferramentas do `AIChatPipeline` rodam essa chamada quando o texto inteiro é JSON de chamada e todo `name` é uma ferramenta registrada (#866). O passo da ferramenta sai com `AgentStep.from_text=True`.

O que pode mudar para você: um agente cuja resposta legítima é um objeto JSON com `name` igual ao de uma ferramenta e com chave `arguments` passa a executar essa ferramenta em vez de devolver o JSON. Para manter o comportamento antigo:

```python
from tempest_fastapi_sdk.agents import Agent
from tempest_fastapi_sdk.genai import AIChatPipeline, OllamaGenerator

generator = OllamaGenerator("qwen2.5-coder:14b")
agent = Agent(generator, parse_text_tool_calls=False)
pipeline = AIChatPipeline(generator, parse_text_tool_calls=False)
```

## 0.374.0 — schema estrito na saída estruturada e imagem truncada recusada

| Onde | O que muda | O que fazer |
| --- | --- | --- |
| `OllamaGenerator.chat_structured` / `generate_structured` | O schema enviado no `format` tem **todo campo em `required`** (inclusive os com default e os `X \| None`, que continuam aceitando `null`). O modelo passa a emitir campos que antes omitia — e que o default preenchia em silêncio: no `gpt-oss:20b` a acurácia por campo foi de 70,8 para 95,4 (33 casos, 2026-11-26/27, Ollama 0.30.11) | Nada, na maioria dos casos. Se um campo com default é "o modelo não precisa preencher", o modelo agora preenche: confira campos com default que o seu código trata como sinal de ausência |
| `make_vision_router` com `max_image_pixels` (padrão), `FaceRecognizer`, o carregamento de imagem do `genai` e o `share` | Imagem truncada é recusada mesmo depois de o `weasyprint` (extra `[pdf]`) ter sido importado no processo; antes ela passava. O router responde `422` sem chamar o modelo, ao custo de uma decodificação a mais (~70 ms num JPEG de 12 MP, medido). `FaceRecognizer` e o `genai` decodificam a imagem na hora: a exceção sai na chamada, e uma imagem passada por caminho é lida para a memória | Cliente que mandava imagem truncada passa a receber `422`. Com `max_image_pixels=None` a checagem do router continua desligada |

## 0.373.0 — `BaseController` e `BaseService` ligam `ResponseT` à camada de baixo

Antes, `BaseController` declarava o próprio `ResponseT` independente do service e convertia o retorno com `cast("ResponseT", ...)` — um controller que repetia o schema errado passava no `mypy --strict` e devolvia o schema do service em runtime (#838):

```python
from typing import Any
from uuid import UUID

from tempest_fastapi_sdk import BaseController, BaseSchema, BaseService


class UserResponseSchema(BaseSchema):
    email: str


class OrderResponseSchema(BaseSchema):
    total: int


class UserService(BaseService[Any, UserResponseSchema]):
    pass


class WrongController(BaseController[UserService, OrderResponseSchema]):
    pass


async def total(controller: WrongController, id: UUID) -> int:
    return (await controller.get_by_id(id)).total  # docs-guard: skip
```

Agora `get_by_id`, `list` e `update` em `BaseController` leem o tipo de resposta (e, no `update`, o schema de update) direto do `ServiceT`. No exemplo acima, o `mypy --strict` recusa com `"UserResponseSchema" has no attribute "total"  [attr-defined]` e o `basedpyright` com `Cannot access attribute "total" for class "UserResponseSchema"`.

As formas existentes `BaseController[Service, Resp]`, `BaseController[Service, Resp, Update]` e `BaseRepository[Model]` continuam aceitas por compatibilidade quando concordam com o service. A forma recomendada fica mais curta e amarra também o repository:

```python
from sqlalchemy import String
from sqlalchemy.orm import Mapped, mapped_column

from tempest_fastapi_sdk import (
    BaseController,
    BaseModel,
    BaseRepository,
    BaseResponseSchema,
    BaseSchema,
    BaseService,
)


class UserModel(BaseModel):
    __tablename__ = "migration_users_example"

    email: Mapped[str] = mapped_column(String(64), nullable=False)


class UserResponseSchema(BaseResponseSchema):
    email: str


class UserUpdateSchema(BaseSchema):
    email: str | None = None


class UserRepository(BaseRepository[UserModel, UserResponseSchema]):
    def map_to_response(self, instance: UserModel) -> UserResponseSchema:
        return UserResponseSchema.model_validate(instance)


class UserService(
    BaseService[UserRepository, UserResponseSchema, UserUpdateSchema]
):
    pass


class UserController(BaseController[UserService]):
    pass
```

Se um controller seu falhar após a atualização:

- **Controller apontava para o schema errado:** corrija o service ou passe só `BaseController[SeuService]`, deixando a resposta e o update virem do service.
- **Controller 2-arg sobre service 3-arg chamando `update`:** `controller.update(id, payload)` agora exige o `UpdateT` do service em vez de aceitar qualquer `BaseSchema`; passe o schema de update concreto.
- **Service com `BaseRepository[Model, Resp]` diferente do `ResponseT` do service:** no `basedpyright`, o call site passa a recusar o acesso aos métodos de leitura/mapeamento até os dois concordarem.

## 0.373.0 — `ObjectStat.raw` pode ser `None`

`ObjectStat.raw` agora é anotado `minio.datatypes.Object | None` (#836). Em runtime nada mudou: o `AsyncMinIOClient` continua preenchendo o `Object` do `minio`, e o `LocalObjectStorageClient` e o `FakeObjectStorageClient` continuam devolvendo `None`, como já faziam. O que muda é o checker: leitura sem checagem, como `stat.raw.version_id`, passa a ser `error: Item "None" of "Object | None" has no attribute "version_id"  [union-attr]` no mypy. Antes ele aceitava a linha, que levantava `AttributeError` contra o backend local e o fake.

Estreite antes de ler:

```python
from tempest_fastapi_sdk.storage import ObjectStat


def version_of(stat: ObjectStat) -> str | None:
    if stat.raw is None:
        return None
    return stat.raw.version_id
```

Se você já fazia essa checagem e silenciava o `unreachable` do mypy (`warn_unreachable`) com `# type: ignore`, o ignore deixa de ser necessário.

## 0.373.0 — `same_site` do `SignedCookieSessionStore` tipado como `Literal`

O parâmetro `same_site` de `SignedCookieSessionStore` era `str` e passa a ser `SameSite` (`Literal["lax", "strict", "none"]`, exportado em `tempest_fastapi_sdk`). Valor fora dos três agora levanta `ValueError` na construção, em vez de `AssertionError` no primeiro login. O mypy recusa (`arg-type`) duas formas que antes passavam:

- **Variável `str`:** anote-a como `SameSite`, ou leia o valor de um campo de settings já tipado assim (o `SESSION_COOKIE_SAMESITE` do `SessionSettings` é `SessionCookieSameSite`, o mesmo `Literal`).
- **Grafia com maiúscula (`"Lax"`, `"Strict"`):** escreva em minúscula. Em runtime ela continua aceita e é guardada em minúscula, então o cabeçalho `Set-Cookie` passa de `SameSite=Strict` para `SameSite=strict`.

```python
from tempest_fastapi_sdk import SameSite
from tempest_fastapi_sdk.admin import SignedCookieSessionStore

policy: SameSite = "strict"
store: SignedCookieSessionStore = SignedCookieSessionStore(
    "change-me-to-a-32-byte-secret-key!!",
    same_site=policy,
)
```

## 0.373.0 — `BaseUserModel` sem colunas fantasmas

`BaseUserModel` declarava `totp_secret`, `totp_enabled_at`, `totp_last_step` e `name` só para o checker. Em runtime essas colunas vêm de `MFAMixin` e `NameMixin`, então um model sem o mixin passava no `mypy --strict` e levantava `AttributeError` na linha:

```python
from tempest_fastapi_sdk import BaseUserModel


class UserModel(BaseUserModel):
    __tablename__ = "users"


def label(user: UserModel) -> str:
    return user.name  # docs-guard: skip
```

Agora o `mypy --strict` recusa essa linha com `"UserModel" has no attribute "name"  [attr-defined]`. O código já quebrava em runtime; a mudança só move o erro para o checker. Escolha uma das duas saídas:

- **O model tem a coluna:** herde o mixin (`class UserModel(NameMixin, BaseUserModel)`, ou `MFAMixin` para os `totp_*`) e gere a migration.
- **A função aceita qualquer `BaseUserModel`:** estreite antes de ler.

```python
from datetime import datetime

from tempest_fastapi_sdk import BaseUserModel, MFAMixin, NameMixin


def display(user: BaseUserModel) -> str:
    if isinstance(user, NameMixin):
        return user.name
    return user.email


def enabled_at(user: BaseUserModel) -> datetime | None:
    if isinstance(user, MFAMixin):
        return user.totp_enabled_at
    return None
```

O SDK passou a ler as colunas do mesmo jeito, e isso muda três comportamentos para model **sem** o mixin:

- `UserAuthService.mfa_enroll` levanta `TypeError` antes de gravar qualquer linha. Antes devolvia um segredo sem coluna onde morar e gravava os recovery codes. `mfa_confirm` responde `422` (`MFA not initialized`), e `mfa_disable` / `mfa_reset`, que levantavam `AttributeError`, respondem `422` (`MFA not active`).
- Model que declara a **própria** coluna `name`, sem `NameMixin`, registra a passkey (`WebAuthnService.register_begin`) com o e-mail como `display_name`. Para manter o nome, troque a coluna própria por `NameMixin`.
- `tempest user create --require-mfa` e `tempest user mfa-reset` exigem `MFAMixin` na classe; colunas `totp_*` declaradas à mão não bastam mais.

## 0.373.0 — quebras de runtime fora do checker e tipos públicos estreitados

Três mudanças desta release quebram em **runtime**, não só no type-checker:

| Onde | O que muda | O que fazer |
| --- | --- | --- |
| `recall_prompt(memory, ...)` | Chama `memory.search(user_id=..., query=..., top_k=...)` — o método que `ChatMemory` e `PgChatMemory` têm — em vez de `memory.recall(...)`, que nenhuma classe do SDK tinha. Memória própria que implementava só `recall` agora levanta `AttributeError` (antes devolvia `""` em silêncio); falha de um backend com `search` continua devolvendo `""`, com um `WARNING` no logger `tempest_fastapi_sdk.agents.memory` | Implemente `search(*, user_id, query, top_k)` devolvendo os `MemoryHit`, ou passe um `ChatMemory`/`PgChatMemory`. O Protocol `SupportsMemorySearch` descreve o formato |
| Agente e `AIChatPipeline` com ferramentas | Decidem por `isinstance(generator, ToolCallingBackend)`, que exige `chat` **e** `chat_with_tools`. Um dublê só com `chat_with_tools` deixa de rodar o loop de ferramentas | Dê ao dublê também `async def chat(self, messages, /) -> str` |
| `FakePixProvider.parse_webhook(event)` | Recebe `object` e levanta `TypeError` (`parse_webhook expects a mapping, got str.`) para o que não for `Mapping` | Passe o corpo do webhook já decodificado como `dict` |

O resto das mudanças de tipo desta release (#839, #841, #842 e a parte de settings de #843) só aparece no `mypy`/`basedpyright`: retornos e parâmetros públicos que eram `Any` ganharam tipo, e os `*_kwargs()` dos settings devolvem `TypedDict` — leitura por chave e o splat `**` continuam funcionando; quebra só quem inseria chave nova no dict devolvido. Cada item, com a nota de migração própria, está no [changelog](../changelog.md) da 0.373.0.

## 0.372.0 — cinco regras novas no `tempest check` e `RuntimeError` sem URL no `AlembicHelper`

O `tempest check` (e o `tempest lint-layers`) ganhou cinco regras, todas de severidade `warning`. Com `layers_strict = true` em `[tool.tempest]`, que é o padrão do `tempest new`, aviso também derruba o comando: num projeto gerado com só três avisos plantados, `tempest lint-layers` imprimiu `3 layer finding(s): 0 error(s), 3 warning(s).` e saiu com código `1`; com `layers_strict = false`, com código `0`.

| Regra | O que acusa | O que fazer |
| --- | --- | --- |
| `INIT001` | `def`, `class`, chamada ou constante em `__init__.py` | Mova para um módulo do pacote (`router.py`, `factory.py`, `runner.py`) e deixe o `__init__.py` só com `from .x import Y as Y` e `__all__` |
| `SIZE001` | Módulo do código ou da suíte com mais de 1000 linhas | Divida por responsabilidade: um service em vários, um arquivo de teste em um por tema |
| `LAY003` | Arquivo de `controllers/`, `services/`, `repositories/` ou `models/` com o sufixo da camada no nome (`checkout_service.py`) | Renomeie para `checkout.py`; a classe continua `CheckoutService` |
| `RTR005` | `fastapi.APIRouter(...)` num router de domínio, fora do `build_api_router` | Troque por `TempestAPIRouter` (`from tempest_fastapi_sdk import TempestAPIRouter`), que transforma o `@raises(...)` em `responses=` |
| `RTR006` | `summary=` ou `description=` no decorator da rota | Mova o texto para uma constante `EndpointDoc` em `api/docs/<router>.py` e espalhe com `**docs.NOME` |

Para migrar aos poucos, declare o caso em `tests/architecture_exceptions.py`, com o motivo (veja [Exceção declarada](../recommended-architecture.md#excecao-declarada)), ou desligue `layers_strict` enquanto corrige.

`RTR003` e `RTR004` passaram a reconhecer `TempestAPIRouter` e as subclasses de router do projeto, então podem aparecer achados novos em routers que antes passavam.

**`AlembicHelper` sem URL:** sem `db_url=` e sem `DATABASE_URL` resolvível, `current`, `current_async`, `has_existing_schema`, `adopt`, `sync_schema` e `sync_schema_async` levantam `RuntimeError` (`DATABASE_URL is empty. ...`) em vez de `sqlalchemy.exc.ArgumentError`. Em `sync_schema` e `sync_schema_async` isso vale quando há ao menos uma revision: sem nenhuma, os dois devolvem `no_migrations` antes de ler a URL, como já faziam. Quem capturava `ArgumentError` nesse caminho troca para `RuntimeError`.
