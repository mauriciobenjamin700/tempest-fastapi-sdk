    CLI¶

    Instalar o tempest-fastapi-sdk[cli] (ou o [cli-ops], no servidor) expõe um console script tempest. Ele faz dois trabalhos: criar um novo serviço em camadas a partir do esqueleto preferido do SDK e rodar os quatro gates de qualidade (ruff check, ruff format, mypy, pytest) sem copiar e colar os mesmos comandos em cada projeto.

    tempest --help                                  # lista todos os comandos
tempest --version                               # mostra a versão do SDK

    A CLI é o extra [cli] (desde a 0.308.0)

    O tempest mora num extra, e não no pacote base. Em desenvolvimento, instale do jeito que você usa (para o servidor, veja [cli-ops]):

    uv tool install "tempest-fastapi-sdk[cli]"   # comando global
uv add --dev "tempest-fastapi-sdk[cli]"      # no grupo dev do projeto

    O motivo é o ruff: o gate (tempest check) vem do tempest-cli, que exige ruff>=0.8.0 em runtime. No pacote base, todo serviço que importa o SDK levava um formatador para produção, e um projeto que fixa ruff<0.8 no grupo dev nem conseguia resolver o lock.

    Sem nenhum dos dois extras, o script continua instalado e explica o que falta, com saída 2 e sem traceback:

    $ tempest --help
error: missing typer, click. The tempest CLI needs the optional [cli-ops] or [cli] extra. Install it with:
  uv add "tempest-fastapi-sdk[cli-ops]"   (on a server, without ruff)
  uv add --dev "tempest-fastapi-sdk[cli]"   (in development, with the gate)
  uv tool install "tempest-fastapi-sdk[cli]"   (as a global command)

    import tempest_fastapi_sdk não precisa de extra nenhum; ler tempest_fastapi_sdk.cli.app (ou importar tempest_fastapi_sdk.cli.main) sem o typer levanta ImportError com essa instrução. Importar .lint ou .pr_prompt, ou ler TempestConfig / load_tempest_config de tempest_fastapi_sdk.cli.config, sem o tempest-cli levanta ImportError apontando o [cli].

    Erro de uso? O help completo aparece junto

    Quando você digita um comando inexistente, uma opção inválida ou esquece um argumento obrigatório, o tempest imprime o --help completo daquele comando (todos os parâmetros, defaults e descrições) antes da linha de erro — em vez do Try '... --help' enxuto do Click. Você corrige na hora, sem reexecutar com --help.

    tempest user create            # esqueceu --email
# ... help completo do `user create` (todas as opções) ...
# Error: Missing option '--email' / '-e'.

    Servidor x desenvolvimento: [cli-ops] e [cli]¶

    O tempest faz dois tipos de trabalho, e eles moram em ambientes diferentes:

    • Operar o serviço — tempest doctor, tempest db, tempest shell, tempest user, tempest routes e os comandos do próprio projeto ([tool.tempest] commands). Isso você quer no servidor, com a configuração e a rede de lá.
    • O gate de qualidade — lint, fix, format, fmt-check, type, test, check e pr-prompt. Isso é ruff, mypy e pytest, e mora no desenvolvimento e na CI.

    Por isso existem dois extras:

    Extra Traz Onde usar
    [cli-ops] typer, click dependência de runtime, na imagem de produção
    [cli] [cli-ops] + tempest-cli (que exige ruff) grupo dev e uv tool install

    O [cli] contém o [cli-ops], então o projeto declara os dois sem conflito:

    [project]
dependencies = [
    "tempest-fastapi-sdk[cli-ops,postgres]",
]

[dependency-groups]
dev = [
    "tempest-fastapi-sdk[cli]",
]

    Com uv sync --no-dev (o que o Dockerfile gerado roda), a imagem fica com o tempest e sem tempest-cli nem ruff. Num venv limpo com só o [cli-ops], import ruff e import tempest_cli falham, e o resto funciona:

    $ tempest doctor
OK    python         3.12.7 (...)
OK    sdk            tempest-fastapi-sdk <versão>
SKIP  settings       no <root>/core/settings.py here — run inside the project root
...
$ tempest staff-create ana@example.com      # de [tool.tempest] commands
staff created: ana@example.com

    Os comandos do gate continuam listados no tempest --help — com a ajuda Quality gate command; needs the [cli] extra (tempest-cli and ruff). — e, chamados, explicam o que falta em vez de sumir num No such command. Saem com código 2, sem traceback, com qualquer argumento que você tenha passado:

    $ tempest lint
error: tempest lint is not available. The quality gate (lint, fix, format, fmt-check, type, test, check, pr-prompt) needs the optional [cli] extra, which adds tempest-cli and ruff. Install it with:
  uv add --dev "tempest-fastapi-sdk[cli]"   (in a project)
  uv tool install "tempest-fastapi-sdk[cli]"   (as a global command)

    Pré-compile o bytecode na imagem: UV_COMPILE_BYTECODE=1

    O uv não compila os .pyc ao instalar, então o Python compila cada módulo na primeira vez que o importa. Se o container roda com um usuário sem permissão de escrita no site-packages — o caso comum numa imagem com usuário não-root —, os .pyc nunca são gravados e toda execução paga essa compilação, não só a primeira. Medido com tempest-fastapi-sdk[cli-ops]==0.326.0, tempest --help, 3 rodadas de cada:

    Instalação 1ª execução Seguintes
    sem UV_COMPILE_BYTECODE ~0,34 s ~0,14 s
    sem, com site-packages só leitura ~0,34 s ~0,34 s
    com UV_COMPILE_BYTECODE=1 ~0,14 s ~0,14 s

    O Dockerfile que o tempest new gera já liga a variável. Num Dockerfile seu, ou num uv pip install / uv tool install, ligue-a no passo de instalação, para a compilação acontecer uma vez, no build:

    ENV UV_COMPILE_BYTECODE=1
RUN uv sync --locked --no-dev

    O mecanismo é o mesmo para todo módulo que a app importa ao subir, não só para o tempest.

    Detalhes técnicos

    A leitura do [tool.tempest] que acha o projeto e os commands (find_pyproject, load_tempest_table, load_project_commands em tempest_fastapi_sdk.cli.config) é código do SDK, só com a stdlib, portada do tempest-cli. O typing_strictness e as flags de ruff/mypy continuam sendo do tempest-cli e só carregam quando um comando do gate roda.

    Gerar um novo serviço¶

    tempest new my_service                          # gera em ./my_service
tempest new my_service --path ~/projects        # diretório-pai customizado
# HOST/PORT padrão no .env.example e extras do SDK fixados no pyproject.toml
tempest new my_service --bind-host 0.0.0.0 --bind-port 9090 --extras upload
tempest new my_service --force                  # sobrescreve diretório existente

    O CLAUDE.md gerado é o contrato do projeto

    Todo projeto novo nasce com um CLAUDE.md que fixa as regras que mantêm os serviços parecidos entre si: a direção das dependências entre camadas, a ordem exata dos sete passos de uma feature nova (schema → model → repository → service → controller → provider → router), a tabela do que não reimplementar porque o SDK já entrega, e o "definition of done" que termina em tempest check.

    Ele existe para um agente de IA ler antes de escrever a primeira linha — e por isso os exemplos dele são verificados na CI do SDK: tests/cli/test_scaffold_runtime.py escreve o domínio de exemplo num projeto scaffoldado e o executa (POST 201, duplicado 409 com o code certo, listagem paginada no envelope do SDK). Um símbolo renomeado no SDK quebra o teste, não o projeto de quem usa.

    O pyproject.toml gerado fixa a versão atual do SDK com os extras que você pediu, e só eles (tempest-fastapi-sdk>=<versão> sem --extras). admin e auth são opt-in: com --extras auth o projeto ganha o UserModel, o JWTSettings no Settings e o bloco JWT_* no .env.example; com --extras admin o src/api/app.py também monta o painel admin — e o auth entra junto, porque o login do painel verifica a senha pelo PasswordUtils. Sem nenhum dos dois, o serviço nasce sem tabela de usuário, sem painel e sem bcrypt/PyJWT no lock: --extras postgres fixa só [postgres], --extras admin,cache fixa [admin,auth,cache], e duplicatas somem com a lista saindo em ordem alfabética. Até a 0.312.x admin e auth eram fixados sempre. O grupo dev ganha tempest-fastapi-sdk[cli]>=<versão>, para o tempest rodar no projeto sem entrar na imagem: o Dockerfile gerado instala com uv sync --no-dev. O .env.example criado usa a nomenclatura de settings da v0.8.0 (SERVER_HOST/SERVER_PORT/SERVER_DEBUG/SERVER_RELOAD/LOG_LEVEL/…), e src/server.py delega a tempest_fastapi_sdk.run_server para que o uvicorn seja importado de forma preguiçosa e os testes possam importar o app sem ele. Regras de validação: o nome do projeto deve casar com ^[a-z][a-z0-9_]*$ e não pode colidir com uma palavra-chave do Python, então tempest new Bad-Name e tempest new class saem com código 2 antes de qualquer arquivo ser escrito.

    Título, descrição e versão da API

    A partir da v0.48.0 o Settings scaffoldado carrega TITLE, VERSION e DESCRIPTION, e src/api/app.py os consome (FastAPI(title=settings.TITLE, version=settings.VERSION, description=settings.DESCRIPTION), make_health_router(version= settings.VERSION) e, com [admin], AdminSite(title=f"{settings.TITLE} admin")).

    A versão tem uma fonte só: o VERSION do Settings sai de [project].version no pyproject.toml, lido por read_project_version. O caminho é ancorado no próprio settings.py (não no cwd), então a versão é a do projeto mesmo rodando de outro diretório; bumpar a release é editar o pyproject.toml, e o /health/readiness e o info.version do OpenAPI acompanham. Título e descrição continuam no .env, e a env VERSION ainda sobrepõe o arquivo quando você precisa publicar uma versão diferente do que está commitado:

    TITLE=Minha API
DESCRIPTION=API de pagamentos do produto X.
# VERSION=1.2.0  # opcional: sobrepõe [project].version

    docker-compose.yaml baseado nos extras¶

    Desde a v0.25.0 o scaffold gera um docker-compose.yaml com apenas os serviços que os extras escolhidos precisam — sem ZooKeeper, Kafka ou qualquer outra coisa que você não vai usar.

    Extra Container subido Porta(s) publicada(s) em 127.0.0.1
    (sempre) postgres:18-alpine 5432
    [cache] / [tasks-redis] redis:8-alpine 6379
    [queue] / [tasks] rabbitmq:4-management-alpine 5672 (AMQP) + 15672 (UI)
    [minio] quay.io/minio/minio + bootstrap mc 9000 (API) + 9001 (Console)
    [email] mailhog/mailhog 1025 (SMTP) + 8025 (UI)

    Toda porta da infra é publicada só no loopback ("127.0.0.1:5432:5432"): o processo que você roda no host continua alcançando o Postgres em localhost:5432, e nada de fora da máquina alcança. A API não precisa dessas portas — dentro do compose ela fala com a infra pelo nome do serviço (veja o profile prod).

    Exemplo — projeto que usa cache + uploads em S3 + emails:

    tempest new my_service --extras auth,cache,minio,email

    Gera:

    • postgres, redis, minio (+ minio-bootstrap que cria o bucket uploads), mailhog
    • .env.example com REDIS_URL, MINIO_ROOT_* (o container), STORAGE_* (o app), SMTP_HOST=localhost, SMTP_PORT=1025, SMTP_USE_TLS=false (MailHog é plain — sem STARTTLS)

    Credenciais vêm do .env, não estão hardcoded no compose

    A partir da v0.37.0, nenhuma credencial é gravada direto no docker-compose.yaml. Cada bloco environment: usa a forma ${VAR:-default}, e o Docker Compose resolve VAR a partir do .env ao lado do compose. O :-default mantém o stack subindo antes de você copiar .env.example para .env — mas defina segredos reais no .env para qualquer deploy não-descartável. Variáveis lidas pelo compose: POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB, RABBITMQ_DEFAULT_USER / RABBITMQ_DEFAULT_PASS / RABBITMQ_DEFAULT_VHOST, MINIO_ROOT_USER / MINIO_ROOT_PASSWORD — todas com seus padrões já no .env.example.

    Subir só a infra — o fluxo de dev, com a app rodando no host e reload:

    docker compose up -d
uv run python main.py

    Derrubar mantendo volumes:

    docker compose --profile prod down

    Derrubar limpando volumes:

    docker compose --profile prod down -v

    down sem --profile prod deixa a API de pé

    Um docker compose down puro não enxerga o serviço api: ele derruba a infra, deixa o container my_service-api rodando e a rede termina em Resource is still in use. Passar --profile prod no down funciona nos dois casos — com ou sem a API no ar.

    Profile prod: a API dentro do compose¶

    O compose também traz a própria API, como um serviço api atrás de profiles: ["prod"]. Sem o profile ele não existe — docker compose up -d continua subindo só a infra, como acima. Com o profile, o Dockerfile do projeto é construído e a app sobe na rede do compose, ao lado da infra:

    cp .env.example .env
docker compose --profile prod up -d --build --wait
curl http://127.0.0.1:8000/health/readiness

    {"status":"ready","checks":{"database":true},"version":"0.1.0"}

    Para tempest new my_service --extras cache,tasks, o bloco gerado é:

    services:
  api:
    # Only under `docker compose --profile prod up -d --build`;
    # plain `docker compose up -d` keeps running just the infra.
    profiles: ["prod"]
    build: .
    container_name: my_service-api
    restart: unless-stopped
    env_file: .env
    environment:
      # environment: wins over env_file. .env points every backend
      # at localhost (right for the host, wrong in a container), so
      # the hosts are re-pointed at the compose service names here.
      # SMTP_* is left to .env on purpose: MailHog is dev-only and
      # production mail goes through the real SMTP server.

    Pedaço por pedaço:

    • environment: reescreve os hosts. O .env que o scaffold gera aponta tudo para localhost — certo para o processo no host, errado dentro de um container, onde localhost é o próprio container da API. O Compose dá precedência ao environment: sobre o env_file:, então cada host que o .env.example aponta para localhost é trocado pelo nome do serviço, só para os extras escolhidos:

      Variável Valor dentro do compose Quando
      DATABASE_URL postgresql+asyncpg://…@postgres:5432/<db> sempre
      REDIS_URL redis://redis:6379/0 [cache]
      RABBITMQ_URL / TASKIQ_BROKER_URL amqp://…@rabbitmq:5672/ [queue] / [tasks]
      TASKIQ_BROKER_URL redis://redis:6379/0 [tasks-redis] (vence o amqp:// do [tasks])
      STORAGE_ENDPOINT minio:9000 [minio]

      Sem essa reescrita a API não quebra — ela sobe no lugar errado. A mesma imagem rodada só com --env-file .env respondeu {"status":"ready","checks":{"database":true}} com 200 e criou /app/app.db dentro do container: o DATABASE_URL default do .env é SQLite, e o Postgres nunca foi tocado.

    • SERVER_HOST: 0.0.0.0 e SERVER_PORT. O Dockerfile já define SERVER_HOST=0.0.0.0, mas o .env traz SERVER_HOST=127.0.0.1 e vence o ENV da imagem — o uvicorn sobe em http://127.0.0.1:8000 dentro do container e a porta publicada não responde. Fixar os dois no environment: resolve. Isso não contradiz o bind 127.0.0.1 dos templates: aquele vale para o processo no host; dentro do container o bind precisa aceitar a rede do compose.

    • depends_on com condition: service_healthy, um por serviço de extra (todos têm healthcheck). Com [minio], a API também espera o minio-bootstrap terminar (service_completed_successfully), para o bucket uploads existir antes do primeiro request.
    • healthcheck em /health/readiness, via urllib. A python:3.13-slim não tem curl. O scaffold monta o make_health_router, que serve /health/liveness e /health/readiness — /health sozinho responde 404. A readiness responde 503 enquanto o banco não atende, e o urlopen levanta nesse caso, então healthy significa que a app alcançou o Postgres. Ela checa só o banco: Redis, RabbitMQ e MinIO não entram no payload do scaffold.
    • env_file: .env é obrigatório no profile. Sem .env, docker compose --profile prod config falha com env file .../.env not found; o docker compose up -d de dev continua funcionando sem ele.

    Decisões do profile prod

    • Rede default do Compose, sem bloco networks:. Os nomes de serviço já resolvem nela; rede nomeada só faria sentido se outro compose precisasse se juntar a esta.
    • Infra só em 127.0.0.1, API em todas as interfaces. O dev no host continua alcançando banco e broker; em produção eles não ficam expostos para fora da máquina. A porta da API é publicada normalmente — é ela que serve tráfego.
    • MailHog sem profile, e o SMTP fica com o .env. O MailHog sobe nos dois modos (o fluxo de dev não muda), mas o environment: da API não reescreve SMTP_*: dentro do container o SMTP_HOST=localhost do .env.example não alcança o MailHog. Em produção configure no .env o servidor SMTP real; para testar e-mail com o MailHog dentro do compose, use SMTP_HOST=mailhog no .env.
    • asyncpg é dependência do projeto gerado. O pyproject.toml do scaffold declara asyncpg>=0.30.0 ao lado do aiosqlite, porque a imagem instala só o que o pyproject.toml declara e o profile prod sempre usa postgresql+asyncpg://.
    Migrations no profile prod¶

    O scaffold já vem com alembic.ini, alembic/ e uma revision baseline (as tabelas dos models que os extras trouxeram — users com [auth], um upgrade() vazio sem ele), e o lifespan do src/api/app.py gerado chama AlembicHelper(...).sync_schema_async() antes do db.connect(). Então o compose não precisa de serviço de migration: a API migra o Postgres ao subir.

    cp .env.example .env
docker compose --profile prod up -d --build --wait
curl http://127.0.0.1:8000/health/readiness

    Medido com tempest new my_service --extras admin,postgres: a API respondeu /health/readiness 200, o Postgres ficou com users e alembic_version na revision baseline, e reiniciar a API não rodou nenhum upgrade de novo. O sync_schema_async recusa migration destrutiva (drop de tabela, coluna ou constraint) e trata banco vazio, banco criado antes do Alembic e banco já migrado. Com várias réplicas subindo juntas, desligue com DATABASE_MIGRATE_ON_STARTUP=false e rode docker compose --profile prod run --rm api tempest db upgrade num job.

    Model novo ganha migration com tempest db revision -m "..."; a próxima subida aplica.

    As tags das imagens são fixadas — atualize por pyproject.toml da SDK, não no projeto gerado. Versões atuais (v0.26.0+): postgres:18-alpine, redis:8-alpine, rabbitmq:4-management-alpine.

    Dockerfile para containerizar a app¶

    Fullstack: a SPA é detectada e compilada num stage Node

    Se o projeto tem um frontend — um package.json em web/, frontend/, client/ ou ui/ — o Dockerfile gerado ganha um stage Node que instala e compila a SPA, e só o dist/ resultante é copiado para a imagem final. Nem node_modules nem o toolchain do Node chegam ao runtime.

    Opção Efeito
    (nenhuma) Detecta pelo package.json. Diretório vazio não conta
    --spa-dir apps-web Layout fora da convenção

    Sirva o resultado com make_spa_router("web/dist"), incluído depois de todos os routers de API. Projeto sem frontend não ganha stage spa nem COPY --from=spa: o Dockerfile sai só com os stages builder e final mostrados abaixo.

    Desde a v0.71.0, tempest new também gera um Dockerfile + .dockerignore prontos pra empacotar o serviço como imagem. O Dockerfile é multi-stage e usa uv:

    • stage builder — instala as dependências num /app/.venv (camada cacheada que só re-roda quando pyproject.toml / uv.lock mudam), depois instala o projeto.
    • stage final — copia só o venv + o código, cria /app/logs e passa /app para o usuário não-root (app, uid 1000), que então consegue escrever o logs/ e o app.db do SQLite, e expõe a porta configurada.

    O arquivo gerado para my_service, colado da saída do gerador:

    # Dockerfile — generated by `tempest new` for my_service.
#
# Multi-stage build using uv (https://docs.astral.sh/uv/):
#   * builder stage installs dependencies into /app/.venv
#   * final stage copies only the venv + source, runs as a non-root user
#
# Build:  docker build -t my_service .
# Run:    docker run --rm -p 8000:8000 --env-file .env my_service
# Or, with the infra:  docker compose --profile prod up -d --build
#
# The image binds SERVER_HOST=0.0.0.0 (see the final stage) so the app is
# reachable from outside the container even without a .env file. The `api`
# service in docker-compose.yaml (prod profile) builds this image and
# re-points DATABASE_URL & co. from the .env's localhost to the compose
# service names; a bare `docker run --env-file .env` does not, so it only
# reaches the infra if you edit those hosts yourself.

# ---- builder ----------------------------------------------------------------
FROM python:3.13-slim AS builder

# uv ships as a static binary; pin the tag in production for reproducibility.
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/

# Copy bytecode-compiled packages instead of symlinking — the venv must be
# self-contained when copied across stages.
ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy

WORKDIR /app

# Install dependencies first (without the project) so this layer is cached
# and only re-runs when pyproject.toml / uv.lock change. uv.lock is optional
# in a fresh scaffold — the glob keeps the COPY from failing when it is absent.
COPY pyproject.toml uv.lock* ./
RUN uv sync --no-dev --no-install-project

# Now copy the source and install the project itself.
COPY . .
RUN uv sync --no-dev

# ---- final ------------------------------------------------------------------
FROM python:3.13-slim

# Run as an unprivileged user. /app is owned by it so the app can write
# logs/ and the default SQLite app.db without root.
RUN useradd --create-home --uid 1000 app

WORKDIR /app
COPY --from=builder --chown=app:app /app /app

# WORKDIR created /app as root before the COPY, and `COPY --chown` only sets
# ownership on the copied *contents* — not on the pre-existing /app directory
# node itself. So the app user cannot create new entries (the runtime logs/
# dir, the default SQLite app.db, etc.) inside /app and the app crashes at
# startup with `PermissionError: [Errno 13] ... 'logs'`. Chown the directory
# and pre-create logs/ so the SDK's file logging (LOG_DIR=logs) works.
RUN mkdir -p /app/logs && chown -R app:app /app

# Put the venv on PATH so `python` resolves to the project interpreter.
# SERVER_HOST=0.0.0.0 binds all interfaces inside the container so the app
# is reachable from the host (overridable via .env / `environment:`).
ENV PATH="/app/.venv/bin:$PATH" \
    SERVER_HOST=0.0.0.0 \
    SERVER_PORT=8000

USER app
EXPOSE 8000

CMD ["python", "main.py"]

    Construir e rodar:

    docker build -t my_service .
docker run --rm -p 8000:8000 --env-file .env my_service

    A imagem faz bind em 0.0.0.0 por padrão

    O stage final define ENV SERVER_HOST=0.0.0.0 para que a app seja acessível de fora do container mesmo sem .env. Localmente o scaffold mantém SERVER_HOST=127.0.0.1 (serviço interno) — o container sobrescreve pra 0.0.0.0 porque ali o bind precisa aceitar conexões externas. Um --env-file .env sozinho não liga a imagem à infra do docker-compose.yaml: o .env aponta para localhost. Para isso use o profile prod.

    Só que variável de --env-file vence o ENV da imagem: um .env copiado do .env.example traz SERVER_HOST=127.0.0.1 e devolve o bind para dentro do container. Tire o SERVER_HOST do .env que vai para o container, ou ponha SERVER_HOST=0.0.0.0 nele.

    Gerar as camadas src dos extras — tempest generate --src¶

    As camadas sempre presentes (api, controllers, services, schemas, db, core, utils) já vêm no scaffold. As camadas que só fazem sentido com um extra específico — [queue] (FastStream) e [tasks] (TaskIQ) — não entram no esqueleto base: deixar pacotes placeholder vazios em todo serviço contraria as regras de layout. Quando você adiciona um desses extras a um projeto existente (uv add "tempest-fastapi-sdk[queue]"), gere a camada correspondente com:

    tempest generate --src                           # lê extras do pyproject.toml local
tempest generate --src --extras tasks            # força extras explícitos
tempest generate --src --force                   # sobrescreve arquivos existentes
tempest generate --docker --src                  # compose + camadas numa tacada

    Mapeamento extra → camada gerada:

    Extra Arquivos criados (sob src/ ou app/)
    [queue] queue/__init__.py (RabbitBroker + AsyncQueueManager + get_broker), queue/handlers.py (subscriber de exemplo)
    [tasks] / [tasks-redis] tasks/queue.py (tq = TaskQueue.from_settings(settings) + get_task_queue), tasks/names.py (EXAMPLE_TASK_NAME, EXAMPLE_SCHEDULE; não importa nada do projeto), tasks/example.py (só o registro: @tq.cron(EXAMPLE_SCHEDULE, name=EXAMPLE_TASK_NAME) chamando scripts/example.py), tasks/dispatch.py (TaskDispatcher: a API enfileira pelo nome, com enqueue_by_name), tasks/worker.py (importa as tasks; broker/scheduler para taskiq worker src.tasks.worker:broker), tasks/__init__.py (reexporta fila, nomes e dispatcher — nunca uma task)

    Os dois extras geram a mesma camada: o transporte sai do TASKIQ_BROKER_URL em runtime. Com [tasks-redis], o tempest new também declara TASKIQ_BROKER_URL no Settings com default redis://localhost:6379/0 e escreve a mesma URL no .env.example, porque o default do mixin é amqp://, que escolhe o RabbitMQ e exige [tasks]. Se mesmo assim a URL apontar para um transporte cujo extra não está instalado, o ImportError do TaskQueue.from_settings nomeia o TASKIQ_BROKER_URL, o valor lido (senha mascarada) e a URL do outro transporte.

    A raiz (src ou app) é detectada automaticamente, e os imports gerados (from src.queue import broker) já apontam pra ela. A operação é idempotente: arquivos existentes são mantidos a menos que você passe --force, então um handler editado à mão nunca é sobrescrito silenciosamente — o arquivo irmão que ainda não existe é criado normalmente. Extras sem camada associada (ex.: só [cache]) não geram nada e o comando avisa.

    Banco de dados — tempest db¶

    Wrapper Alembic. Usa o AlembicHelper por trás, então a configuração (alembic.ini + env.py) continua sendo a fonte da verdade.

    Resolução do DATABASE_URL na seguinte ordem:

    1. Flag --database-url.
    2. Env var DATABASE_URL.
    3. Settings no core/settings.py do projeto, sob qualquer raiz de código (src ou app). Vale qualquer instância de pydantic_settings.BaseSettings — os nomes settings e config são tentados primeiro, e depois o módulo é varrido por tipo —, ou o resultado de um factory zero-arg que devolva uma (get_settings(), ou qualquer callable anotado com retorno BaseSettings).
    4. DATABASE_URL no .env do projeto.
    5. sqlalchemy.url do alembic.ini.

    O nome da instância não importa mais, e o factory vale

    Até a 0.280.0 só o nome settings era aceito, e a falha era um ImportError engolido por um except Exception: return None. Um serviço que chamasse a instância de config recebia "no database URL. Pass --database-url, set DATABASE_URL, or run inside a project with src/core/settings.py" — apontando para duas condições que o projeto já satisfazia. Hoje o que decide é o tipo da instância, o factory documentado (get_settings()) é aceito, o .env é lido, e quando nada resolve cada tentativa reporta o motivo no stderr:

    note: importing src.core.settings failed: ImportError("cannot import name ...")
error: no database URL. Pass --database-url, set DATABASE_URL, put it in
       .env, or expose settings with a DATABASE_URL on
       src/core/settings.py (or app/core/settings.py).

    A mesma descoberta é compartilhada por tempest db, tempest doctor, tempest user e o env.py gerado — um projeto cujo settings só existe como get_settings() passa a migrar fora do CLI também.

    tempest db init                                  # cria alembic.ini + alembic/env.py

tempest db revision -m "manual change" --manual  # cria arquivo vazio pra editar
tempest db upgrade                               # alembic upgrade head
tempest db upgrade <rev>                         # upgrade até rev específico
tempest db downgrade                             # rollback de 1 step
tempest db downgrade <rev>                       # rollback até rev específico

    stamp head não adota um banco existente

    stamp grava o ponteiro sem rodar nada. Contra um schema que o Alembic não construiu, carimbar head registra como aplicadas revisions que nunca rodaram: o banco fica com as colunas velhas enquanto current, upgrade e history respondem que está em dia, e a falha aparece semanas depois em produção. A revision certa para adoção é a base — veja Migrations », que traz AlembicHelper.adopt() e sync_schema() para não escolher isso à mão.

    Quando o Alembic recusa o comando¶

    Erro do Alembic que descreve o estado do banco — e não um bug — sai como uma linha, com o que fazer:

    $ tempest db revision -m "novo campo" --autogenerate
error: the database is behind head — a migration is pending. Run `tempest db upgrade`, then try again.
       (TEMPEST_DEBUG=1 for the full traceback)
$ echo $?
1

    Quatro condições ganham conselho: banco atrás da head, histórico com mais de uma head, revisão que não existe em alembic/versions/, e revisões que não estão na mesma linhagem. Qualquer outra mensagem sai como o Alembic escreveu, sem tradução — dica errada seria pior que a mensagem crua.

    Quer o traceback de volta?

    TEMPEST_DEBUG=1 tempest db revision ... re-levanta a exceção intocada. Use quando o erro não for uma das condições acima e você precisar ver de onde ele veio.

    Só a CLI traduz

    Chamar AlembicHelper.revision(...) direto, de um script ou do lifespan, continua levantando alembic.util.exc.CommandError. Código quer a exceção tipada; quem está no terminal quer a frase.

    Colapsar o histórico — tempest db squash¶

    Com o tempo o diretório alembic/versions/ cresce sem limite — cada ajuste de schema vira mais um arquivo que o Alembic precisa percorrer em todo upgrade. O squash zera esse histórico para uma única migration raiz que descreve o schema atual, sem perder os bancos já existentes.

    Operação destrutiva — rode contra um banco de desenvolvimento

    O squash faz downgrade base no banco configurado (DROPa todas as tabelas) para conseguir autogerar o schema completo num arquivo só. Por isso exige --yes. Confirme que o DATABASE_URL aponta para um banco de dev antes de rodar.

    O fluxo é:

    1. Captura o head atual (vira o nome do diretório de backup).
    2. downgrade base — limpa o banco para o autogenerate enxergar o schema vazio.
    3. Move as revisions antigas para alembic/versions/_squashed_<oldhead>/ (subdiretório que o Alembic ignora). Use --no-backup para apagar de vez.
    4. Autogera uma migration raiz a partir de BaseModel.metadata.
    5. upgrade head recria o schema e marca a nova revision.
    tempest db squash -m "init" --yes               # backup recuperável (padrão)
tempest db squash -m "init" --yes --no-backup   # apaga os arquivos antigos

    Bancos de produção não são tocados

    O squash só mexe no banco configurado. Depois de fazer deploy da árvore colapsada, marque os bancos de produção como migrados sem recriar tabelas:

    tempest db stamp head

    Squash manual (sem perder dados) → stamp --purge

    Se você unificar as migrations à mão (apaga versions/, escreve 1 migration baseline, mantém o banco com os dados), o alembic_version ainda aponta para a revision antiga — que não existe mais no tree. Um stamp normal falha com Can't locate revision. Use --purge para limpar o ponteiro órfão e gravar o novo baseline:

    tempest db stamp init_schema --purge

    Recap: squash troca um histórico que cresce sem fim por uma migration inicial limpa; stamp reconcilia os bancos que já estão no schema final (use --purge quando a revision gravada não existir mais). Backup recuperável por padrão — o Git é a sua segunda rede.

    Backup e restore — tempest db backup / tempest db restore¶

    Snapshot do banco para um arquivo e volta. A estratégia muda por dialeto, mas a CLI é a mesma:

    • PostgreSQL — pg_dump / pg_restore. O formato vem da extensão do arquivo: .dump → custom (pg_dump -Fc, comprimido, restaura com pg_restore), .sql → plain (psql). Force com --plain / --custom. Exige os client tools do Postgres no PATH.
    • SQLite — cópia do arquivo do banco.

    Pré-requisito: client tools do Postgres

    backup / restore num banco PostgreSQL dependem dos binários pg_dump, pg_restore e psql disponíveis no PATH. Eles não vêm com o pacote Python — são instalados pelo sistema operacional. Sem eles, a CLI falha com uma mensagem clara ('pg_dump' not found on PATH).

    SQLite não precisa de nada — o backup é uma cópia de arquivo feita pela stdlib.

    sudo apt-get update && sudo apt-get install -y postgresql-client

    sudo dnf install -y postgresql

    sudo pacman -S postgresql

    brew install libpq && brew link --force libpq

    choco install postgresql   # Chocolatey
scoop install postgresql   # ou Scoop

    Confira a instalação

    pg_dump --version && pg_restore --version && psql --version
    Combine a versão do client com a do servidor (pg_dump de uma major mais nova lê servidores mais antigos, mas o contrário falha).

    tempest db backup                       # backups/<db>_<YYYYMMDD-HHMMSS>.dump
tempest db backup -o snapshot.sql       # plain SQL (Postgres) pela extensão
tempest db backup -o snap.dump --custom # força formato custom
tempest db restore snapshot.sql --yes   # restaura (psql)
tempest db restore snap.dump --yes      # restaura (pg_restore --clean --if-exists)

    Restore sobrescreve o banco de destino

    Por padrão o restore é clean + recreate: dropa os objetos existentes antes de recriar, então o resultado é uma cópia fiel do backup (pg_restore --clean --if-exists; no plain dropa/recria o schema public; no SQLite sobrescreve o arquivo). Por isso exige --yes. Use --no-clean para aplicar o dump por cima do schema atual.

    A senha do Postgres não vaza no ps

    A URL é parseada em -h/-p/-U/-d e a senha vai via PGPASSWORD no environment do subprocesso — nunca na linha de comando.

    Recap: backup tira um snapshot (formato pela extensão no Postgres, cópia no SQLite); restore --yes traz de volta, limpando o destino por padrão.

    Detectar drift de model — tempest db check¶

    O tempest db revision --autogenerate grava um diff quando você pede. Nada percebe quando alguém edita um model e esquece de pedir — até o deploy que precisava da coluna.

    tempest db check

    Sem drift:

    No drift: the models match the migration tree.

    Com drift, ele nomeia as operações que uma revision conteria e sai com código 1:

    error: New upgrade operations detected: [('add_column', ...'colour'...)]
       Run `tempest db revision -m "<message>"` to record them.

    É um passo de CI

    Rode depois do tempest db upgrade no pipeline. A comparação precisa do banco em head — quando ele está atrás, o Alembic diz isso e a mensagem passa direto, sem virar "drift".

    Popular o banco — tempest db seed¶

    Roda um callable de seed do projeto dentro de uma sessão gerenciada (commit no sucesso, rollback no erro). O callable recebe uma AsyncSession posicional e pode ser sync ou async; o que ele insere é decisão sua — o SDK só cuida do ciclo de vida da sessão. Por padrão importa src.db.seeds:seed.

    from sqlalchemy.ext.asyncio import AsyncSession

from src.db.models import CategoryModel


async def seed(session: AsyncSession) -> int:
    """Popula categorias iniciais. Retorna a contagem (opcional)."""
    session.add_all([CategoryModel(name="Livros"), CategoryModel(name="Games")])
    await session.flush()
    return 2

    Quando o callable devolve um int, a CLI mostra a contagem: Seeded via src.db.seeds:seed (2 rows).

    Usuários — tempest user¶

    Insere/lista usuários direto no banco usando o UserModel concreto do projeto (default src.db.models:UserModel). Útil pra bootstrapear o primeiro admin sem rodar SQL manual.

    # Cria usuário comum
tempest user create --email ana@example.com --password senha-forte-12 --no-admin

# Cria admin (pode logar no /admin)
tempest user create --email admin@local --password admin-pass-12 --admin

# Pede senha interativamente (não fica no shell history)
tempest user create --email admin@local --admin

# Modelo customizado fora do layout scaffoldado — DEVE ser subclasse de BaseUserModel
tempest user create --email x@y --password pass-12-chars --model myapp.models.user:UserModel

# Colunas que o SEU UserModel adiciona — repetível, uma por coluna
tempest user create --email ana@example.com --password senha-forte-12 \
    --set display_name=Ana --set locale=pt-BR

# Promove/rebaixa um usuário existente (liga/desliga is_admin)
tempest user promote --email ana@example.com    # vira admin
tempest user revoke  --email ana@example.com    # volta a ser comum

# Troca a senha de um usuário existente (pede a senha duas vezes)
# e derruba as sessões dele junto
tempest user set-password --email ana@example.com

# Tabela de refresh token fora de src.db.models
tempest user set-password --email ana@example.com \
    --refresh-token-model myapp.models:UserRefreshTokenModel

# Troca a senha e deixa as sessões vivas (opt-out explícito)
tempest user set-password --email ana@example.com --keep-sessions

# Troca a senha e mantém as passkeys (opt-out explícito)
tempest user set-password --email ana@example.com --keep-passkeys

# Primeira conta privilegiada já com MFA + evento de auditoria na mesma transação
tempest user create --email staff@example.com --admin --require-mfa \
    --audit-model src.db.models:AuditLogModel --event staff.bootstrapped

# Conta que perdeu o celular e os recovery codes: remove o segundo fator,
# derruba as sessões e audita na mesma transação

# Lista
tempest user list                                # todos
tempest user list --admin                        # só admins

    Conta com MFA: --require-mfa, set-password e mfa-reset

    create --require-mfa inscreve o segundo fator antes do commit: mostra a URI otpauth:// e o segredo, pede o código do app Authenticator (até 3 tentativas) e só grava com código válido — sem ele, sai com código 1 e nenhuma linha é escrita. Exige MFAMixin no UserModel e a tabela de recovery codes (--recovery-code-model, default src.db.models:UserRecoveryCodeModel); os recovery codes saem uma vez, depois do commit. --audit-model (um BaseAuditLogModel com AuditRequestMixin) grava record_event na mesma transação, com o nome de --event (default user.created); sem ele, o comando avisa no stderr que nenhum evento foi gravado.

    set-password numa conta com MFA ativo (e AUTH_MFA_ENABLED ligado, como no login) pede o código — TOTP ou recovery code — e troca a senha por UserAuthService.change_password_with_mfa. Passo a passo na receita de MFA.

    Quem perdeu o celular e os recovery codes não tem código para dar: mfa-reset é a saída — veja Recuperando quem perdeu o segundo fator abaixo.

    UserModel com coluna própria obrigatória: use --set

    O create preenche email, hashed_password, is_admin e is_active. Toda outra coluna do seu UserModel entra por --set <coluna>=<valor>, validada contra as colunas mapeadas e convertida pro tipo da coluna (bool, int, float, Decimal, UUID, ISO-8601 de data/hora, enum pelo valor e JSON).

    tempest user create -e novato@example.com -p 'senha-forte-12' --no-admin
# error: UserModel requires a value for: display_name.
#        Pass each one as --set <column>=<value>.

    Coluna NOT NULL sem default que você não passou é perguntada num terminal interativo (uma pergunta por coluna) e vira erro com código 2 numa execução sem TTY — em vez do IntegrityError cru que o banco levantava. Chave desconhecida também sai com 2, listando as colunas aceitas; --set email= / --set hashed_password= / --set is_admin= são recusadas apontando a flag dona (--email, --password, --admin/--no-admin).

    Insert recusado pelo banco (email duplicado, quase sempre) sai com código 1 e a mensagem do banco — error: could not insert user: … — em vez de traceback. Os valores do insert não aparecem nela: todo banco que o CLI abre usa hide_parameters=True, então o hash da senha que você acabou de digitar não vai parar no terminal nem no log da CI:

    error: could not insert user: (sqlite3.IntegrityError) UNIQUE constraint failed: users.email
[SQL: INSERT INTO users (email, hashed_password, ...) VALUES (?, ?, ...)]
[SQL parameters hidden due to hide_parameters=True]

    Banco que ainda não foi migrado é detectado antes do insert, com código 1 e nenhuma linha escrita:

    error: table(s) users not found in the database. Run `tempest db upgrade` first; nothing was written.

    Sem --admin/--no-admin, o create pergunta

    Quando você não passa nem --admin nem --no-admin num terminal interativo, o tempest user create pergunta Should this user be an administrator? [y/N]. Em execuções não-interativas (CI, pipes, scripts) o prompt é pulado e o usuário nasce comum (is_admin=False) — passe --admin explicitamente pra criar admin sem TTY.

    tempest user promote / tempest user revoke localizam o usuário por email (case-insensitive) e só alternam is_admin. Quando nenhum usuário casa com o email, saem com código 1 e a mensagem no user found.

    Trocando a senha — tempest user set-password¶

    É o lado do operador do fluxo de reset: a conta pra quem não dá pra mandar link, o primeiro admin trancado fora de um ambiente novo, a credencial rotacionada depois de um incidente. Localiza por email (case-insensitive), hasheia com o set_password do próprio model — o mesmo hash que o login verifica — e sai com código 1 e no user found quando ninguém casa.

    tempest user set-password --email ana@example.com
# Password:
# Confirm:
# Password updated for ana@example.com (id=6f0c...)
# Revoked 2 active refresh token(s).
# Deleted 1 passkey(s).

    Trocar a senha derruba as sessões — por padrão

    Trocar o hash, sozinho, não encerra sessão nenhuma: um access token já emitido continua válido até expirar, e um refresh token guardado no banco continua trocável por um novo — exatamente a janela que o reset existe pra fechar. Por isso a revogação não é uma flag que você precisa lembrar: o comando resolve src.db.models:UserRefreshTokenModel (o nome convencional da tabela opt-in de refresh token — o tempest new não a scaffolda; quem liga a tabela escreve o model com esse nome em src/db/models/) e revoga os refresh tokens do usuário na mesma transação que grava o hash novo.

    • Tabela em outro lugar? --refresh-token-model myapp.models:UserRefreshTokenModel. Spec que você digitou e não resolve é erro com código 2 — nunca degrada em silêncio pra "não revoguei nada".
    • Não quer revogar? --keep-sessions, que é recusado com código 2 se vier junto de --refresh-token-model (as duas flags se contradizem).
    • Projeto que nunca ligou a tabela opt-in de refresh token não tem o que revogar, e o comando diz isso em stderr: note: no refresh-token model at 'src.db.models:UserRefreshTokenModel', so no session was revoked. Pass --refresh-token-model if yours lives elsewhere.

    A contagem é de sessões que esta execução matou — linha já revogada não é recontada, então rodar de novo imprime Revoked 0 active refresh token(s).

    E apaga as passkeys — também por padrão

    A troca feita pelo operador é recuperação de conta, como o mfa-reset: uma passkey entra sem a senha, e a que foi cadastrada por quem segurou a conta sobreviveria ao hash novo. Então o comando apaga todas as passkeys do usuário na mesma transação (UserAuthService.revoke_user_passkeys), pelas mesmas regras das sessões: --webauthn-credential-model (default src.db.models:UserWebAuthnCredentialModel; sem tabela, avisa no stderr que nenhuma passkey foi apagada), --keep-passkeys como saída explícita, e as duas juntas recusadas com código 2. O dono cadastra a passkey de novo depois.

    Auditoria da troca: --audit-model

    Como o mfa-reset, o set-password grava um evento quando recebe --audit-model (um BaseAuditLogModel com AuditRequestMixin): user.password_set por padrão, ou o nome de --event, com actor="cli" e changes={"password_changed": true, "sessions_revoked": N, "passkeys_revoked": M}, na mesma transação do hash novo — se a auditoria falha, a troca é desfeita. --event sem --audit-model sai com código 2.

    tempest user set-password --email ana@example.com \
    --audit-model src.db.models:AuditLogModel

    O mesmo, de dentro do código

    await service.revoke_user_sessions(session, user_id=user.id) é o par administrativo do revoke_refresh_token: logout-everywhere endereçado por id, pra quando você não tem o token em mãos (um endpoint de "desconectar tudo", um agente de suporte trancando conta comprometida). Devolve quantas linhas revogou, e 0 quando o projeto não usa refresh_token_model — JWT stateless não tem linha pra derrubar.

    from uuid import UUID

from sqlalchemy.ext.asyncio import AsyncSession

from tempest_fastapi_sdk import UserAuthService


async def force_logout(
    user_id: UUID,
    session: AsyncSession,
    service: UserAuthService,
) -> int:
    """Revoga todas as sessões de um usuário. Retorna quantas caíram."""
    killed = await service.revoke_user_sessions(session, user_id=user_id)
    await session.commit()
    return killed

    A política de senha é a do seu projeto, não a da CLI

    create e set-password validam o plaintext com check_password_policy contra os três campos AUTH_PASSWORD_* do src.core.settings do projeto — e contra os defaults do PasswordPolicy (mínimo 8 caracteres, máximo 72 bytes) quando o projeto não compõe AuthSettings. É a mesma régua do signup e do painel admin, então a senha que a CLI aceita é sempre uma que o dono da conta consegue usar pra logar.

    O teto é medido em bytes UTF-8, a unidade que o bcrypt conta: 40 caracteres acentuados são 80 bytes e saem com código 2 e error: password must be at most 72 bytes. — antes de qualquer escrita no banco.

    Resolução do DATABASE_URL igual ao tempest db (env var > instância ou factory de settings > .env > alembic.ini).

    Recuperando quem perdeu o segundo fator — tempest user mfa-reset¶

    Conta com MFA ativo cujo dono perdeu o celular e os recovery codes: o set-password pede o código, e não há código para dar. O mfa-reset remove o fator sem prova — por isso pede confirmação e grava quem fez.

    tempest user mfa-reset --email staff@example.com \
    --audit-model src.db.models:AuditLogModel
# Remove the second factor of staff@example.com? It will log in with the password alone until it enrolls again. [y/N]: y
# MFA reset for staff@example.com (id=2ced...)
# Revoked 2 active refresh token(s).
# Deleted 1 passkey(s).

# Fora de um terminal (CI, script): --yes é obrigatório
tempest user mfa-reset --email staff@example.com --yes \
    --audit-model src.db.models:AuditLogModel --event support.mfa_recovered

# Remove o fator e deixa as sessões vivas (opt-out explícito)
tempest user mfa-reset --email staff@example.com --yes --keep-sessions
    • Roda UserAuthService.mfa_reset: limpa totp_secret, totp_enabled_at e totp_last_step e apaga os recovery codes (--recovery-code-model, default src.db.models:UserRecoveryCodeModel; sem tabela, sai com código 2 nomeando a flag).
    • Revoga as sessões por padrão, na mesma transação, com as mesmas regras do set-password: --refresh-token-model (default src.db.models:UserRefreshTokenModel), --keep-sessions como saída explícita, e as duas juntas recusadas com código 2.
    • Apaga as passkeys por padrão, na mesma transação, pelas mesmas regras: --webauthn-credential-model (default src.db.models:UserWebAuthnCredentialModel; sem tabela, avisa no stderr que nenhuma passkey foi apagada), --keep-passkeys como saída explícita, e as duas juntas recusadas com código 2.
    • --audit-model (com AuditRequestMixin) grava record_event na mesma transação, com o nome de --event (default user.mfa_reset); se a escrita da auditoria falha, o reset volta junto. Sem --audit-model, o comando avisa no stderr que nenhum evento foi gravado. --event sem --audit-model sai com código 2.
    • Sem confirmação nada muda: fora de terminal, sem --yes, sai com código 1; no terminal, responder n também sai com 1.
    • Conta sem MFA ativo sai com código 2 (has no MFA active, nothing to reset.); UserModel sem MFAMixin também, antes de abrir o banco. Email desconhecido sai com 1 e no user found.

    Depois do reset a conta entra só com a senha até se inscrever de novo, e o set-password deixa de pedir código. A receita de MFA detalha o caminho, inclusive a chamada direta no código: Conta que perdeu o segundo fator.

    Inspecionar, desativar e apagar¶

    O list responde "quem existe". As quatro abaixo respondem o resto.

    # A linha inteira desse usuário, incluindo as colunas que o SEU model adiciona
tempest user show --email ana@example.com
tempest user show --email ana@example.com --json

# Desliga o acesso (reversível) e derruba as sessões junto
tempest user deactivate --email ana@example.com
tempest user activate --email ana@example.com

# Sessões (refresh tokens) desse usuário
tempest user sessions --email ana@example.com
tempest user sessions --email ana@example.com --revoke

# Apaga a linha (irreversível)
tempest user delete --email ana@example.com --yes

    show redige o hashed_password: nenhuma pergunta que esse comando responde precisa do hash, e imprimi-lo coloca uma credencial no scrollback do terminal e no log do CI.

    deactivate revoga sessão, e não é opcional

    Virar is_active=False não encerra nada sozinho: o refresh token que já foi emitido continua trocável, e a conta que você acabou de desligar continua rendendo access token novo. Por isso a revogação roda na mesma transação que o flag — a mesma regra que o set-password segue.

    sessions sem --revoke lista uma linha por token (id, família, criação, expiração, estado). Usuário sem sessão imprime tabela vazia e sai com 0 — "não está logado em lugar nenhum" é resposta, não erro. A contagem do --revoke é de sessões que aquela execução matou, então rodar duas vezes imprime Revoked 0 na segunda.

    delete é irreversível, e leva os tokens junto

    A tabela de refresh token scaffoldada tem ForeignKey sem ON DELETE CASCADE, então apagar o usuário com token vivo falharia com erro de integridade citando uma constraint em vez da causa. O comando apaga os tokens na mesma transação. Fora de um terminal interativo, --yes é obrigatório. Quando a intenção é "essa pessoa não deve mais entrar", o comando certo é deactivate.

    deactivate bloqueia o login, não é banimento

    Conta desativada não entra, mas o dono pode reativá-la sozinho: o POST /auth/activation/request manda um link de ativação novo para o e-mail da conta, e abrir esse link a deixa ativa de novo. É o comportamento pretendido — quem tem a caixa de e-mail volta. Para fechar a porta de vez, passe refuses_email_link ao UserAuthService com um predicado que case essa conta: ativação e reset por e-mail ficam recusados para ela (veja a receita de MFA).

    Segredos — tempest secrets¶

    Quatro comandos, ordenados por quanto mexem no seu .env:

    Comando Escreve no .env? Quando usar
    generate nunca pegar um valor pra colar num secret manager
    init só o que está vazio ou placeholder logo depois do tempest new
    rotate sempre, com backup o segredo vazou ou envelheceu
    vapid par de chaves Web Push ligar notificação no browser

    Gerar um valor avulso — tempest secrets generate¶

    Não toca em arquivo nenhum: imprime e pronto.

    # Um segredo, valor cru
tempest secrets generate

# Três de uma vez
tempest secrets generate --count 3

# Rotulado, pronto pra colar num .env ou num painel de deploy
tempest secrets generate --keys JWT_SECRET,TOKEN_SECRET

# JSON, pra pipar num secret manager
tempest secrets generate --keys JWT_SECRET --json

    Saída do terceiro:

    JWT_SECRET=_Ptx1Cq4lUAK4EJX7GAnXMp115d6i92I_rrTDJ3sS59noFLm3N1wTWL-F0OhCkbr
TOKEN_SECRET=qNsIyp8hp4BZll_BzcDS7omceBNB4a4EI9JVWvIQEg_R5VveTY0IuLBiogp0uRBa

    Tip

    --count e --keys dizem a mesma coisa (quantos segredos sair), então passar os dois é erro de uso, não um deles vencendo em silêncio.

    Preencher o .env recém-criado — tempest secrets init¶

    O tempest new escreve JWT_SECRET=change-me-change-me-change-me-32 e TOKEN_SECRET= vazio — exatamente os dois casos que o tempest check-config reporta como security.W001 / security.W004. O init troca só esses:

    tempest secrets init

    set JWT_SECRET (was placeholder)
set TOKEN_SECRET (was empty)

    Chave que já tem valor de verdade é mantida, então rodar de novo não faz nada:

    kept JWT_SECRET (already set)
kept TOKEN_SECRET (already set)
Nothing to do.

    Isso é o que separa o init do rotate: o init é seguro de rodar em qualquer momento — inclusive num script de setup — porque nunca destrói segredo em uso. Pra substituir valor real, é opt-in explícito, e aí ele faz backup antes:

    tempest secrets init --force

    Rotacionar — tempest secrets rotate¶

    Gera e reescreve as linhas correspondentes no .env no lugar — fazendo backup do arquivo antigo antes — e deixa as outras linhas intactas.

    # Rotaciona JWT_SECRET e TOKEN_SECRET no .env (gera .env.bak)
tempest secrets rotate

# Só imprime os novos valores (não escreve nada)
tempest secrets rotate --print

# Chaves e arquivo customizados
tempest secrets rotate --keys JWT_SECRET,SESSION_SECRET --env .env.prod

# Mais entropia, sem backup
tempest secrets rotate --length 64 --no-backup

    Warning

    Rotacionar JWT_SECRET invalida todo token assinado com o valor antigo: usuários são deslogados e links de reset/ativação pendentes param de funcionar. Rotacione numa janela de manutenção e reinicie o serviço pra carregar os novos valores.

    Chaves Web Push — tempest secrets vapid¶

    Web Push não usa string aleatória: usa um par de chaves P-256. O browser assina a subscrição com a pública e o servidor assina cada push com a privada, então os dois valores nascem juntos e não saem do generate.

    # Escreve VAPID_PUBLIC_KEY + VAPID_PRIVATE_KEY no .env
tempest secrets vapid

# Com o contato que vai no claim `sub` do JWT VAPID
tempest secrets vapid --subject mailto:ops@example.com

# Só imprime
tempest secrets vapid --print

    São exatamente os campos que o WebPushSettings lê, no formato que o pywebpush lê de volta: privada é o escalar de 32 bytes e pública é o ponto não-comprimido de 65 bytes, ambos em base64url sem padding.

    Danger

    Trocar um par que já existe invalida toda subscrição ativa: o browser que subscreveu com a chave pública antiga não aceita push assinado com a nova, e cada cliente precisa subscrever de novo. Por isso o comando se recusa a sobrescrever sem --force.

    Recap¶

    • generate imprime, init preenche o que falta, rotate troca tudo, vapid gera o par do Web Push.
    • init é idempotente e nunca perde segredo em uso — é o comando do primeiro dia do projeto.
    • rotate e vapid --force são destrutivos de formas diferentes: um desloga usuário, o outro derruba subscrição de push.
    • Todo arquivo que esses comandos escrevem sai 0600.

    Fila e tasks — tempest queue / tempest tasks¶

    # Publica uma mensagem pelo broker do projeto
tempest queue publish orders.paid '{"order_id": 7}' --json
tempest queue handlers                     # canais que este serviço consome

# Tasks de fundo
tempest tasks list                         # nomes registrados
tempest tasks run src.tasks:send_welcome --arg ana@example.com --kwarg retries=2

    O publish conecta, publica e fecha — nessa ordem, num processo só. Fechar é o passo que o script descartável esquece, e é ele que garante o flush da publicação antes do comando retornar.

    O nome da task não é o nome da função

    O TaskIQ registra sob <módulo>:<função> (src.tasks:send_welcome), então o nome que o run recebe não é o que está no arquivo. O list é o que diz qual é qual — e ele importa <root>.tasks.jobs antes de listar, porque task só existe no broker depois que o módulo que a declara foi importado.

    tasks run enfileira, não executa: quem roda é o worker. Comando que retorna com sucesso significa "a mensagem foi aceita", não "o job deu certo".

    Sem --broker / --queue, os dois procuram <root>.queue:broker e <root>.tasks:tq — os nomes que o tempest generate --src escreve. Quando nada resolve, cada tentativa é listada com a causa antes do código 2.

    E-mail — tempest email test¶

    O par que mais custa tempo em configuração de SMTP é STARTTLS (porta 587, SMTP_USE_TLS) contra TLS implícito (porta 465, SMTP_USE_SSL), e o único jeito honesto de saber qual o servidor quer é conectar e mandar.

    tempest email test --to voce@example.com
tempest email test --to voce@example.com --subject "deploy ok" --body "..."
tempest email test --to voce@example.com --html      # exercita o caminho multipart

    Monta o cliente com EmailUtils(**settings.email_kwargs()) — a mesma construção que o serviço faz —, então mensagem que chega aqui chega pela app. Recusa do servidor sai com código 1 carregando a resposta dele, mais a linha que lembra o par TLS.

    Projeto que não compõe EmailSettings sai com código 2 dizendo isso: compor só os mixins que se usa é o normal, não defeito.

    Object store — tempest storage¶

    tempest storage check                       # endpoint responde? bucket existe?
tempest storage ls                          # chaves do bucket default
tempest storage ls relatorios/ --flat       # só o nível imediato
tempest storage put ./nota.pdf --key notas/2026-09.pdf
tempest storage get notas/2026-09.pdf --out ./baixado.pdf
tempest storage presign notas/2026-09.pdf --expires 900
tempest storage rm notas/2026-09.pdf

    Tudo passa pelo AsyncMinIOClient(**settings.storage_kwargs()), então endpoint, credencial, região e — o que mais importa — o endpoint público usado para assinar URL são os do serviço.

    URL assinada com o endpoint interno é válida e inútil

    Assinar contra minio:9000 produz uma URL correta que o browser do usuário não resolve. Configure STORAGE_PUBLIC_ENDPOINT; o presign imprime, no stderr, para qual host ele assinou, justamente para esse erro aparecer antes de ir para o cliente.

    Bucket vazio lista nada e sai com 0 — "nenhum objeto" é resultado, não falha, a mesma convenção dos repositories do SDK.

    Dois comandos agem sobre o backend local (STORAGE_BACKEND=local), pelo LocalObjectStorageClient(**settings.local_storage_kwargs()), e migram o volume para a cifra em repouso:

    tempest storage encrypt-local               # cifra o que está em claro, em todo bucket
tempest storage reencrypt-local --bucket uploads   # passa para a primeira chave

    Os dois são idempotentes e saem com código 2 sem STORAGE_LOCAL_ENCRYPTION_KEYS.

    Feature flags — tempest flags¶

    Flag existe para ser movida sem deploy. Com o backend Redis, essa mudança morava num redis-cli HSET feature_flags <nome> 1 — o tipo de comando que sai com um dígito errado na hora errada.

    tempest flags list                       # tudo que o backend guarda
tempest flags enable new-checkout        # liga para todo processo que lê esse backend
tempest flags disable new-checkout
tempest flags get new-checkout           # estado guardado
tempest flags list --key ff:staging      # outro hash, outro ambiente

    new-checkout  on
legacy-upload off

    Os quatro falam pelo RedisFeatureFlagBackend, então o valor que o serviço lê e o que a CLI escreve passam pelo mesmo código de codificação.

    off e unset são respostas diferentes

    get sai com 1 quando a flag não existe no backend (unset), e com 0 quando ela existe valendo off. A diferença importa: flag não definida resolve para o default que o chamador passou no código; flag em off sobrescreve esse default.

    A URL sai de --redis-url > REDIS_URL > settings do projeto. Redis fora do ar sai com código 2 carregando a mensagem do driver — "connection refused" diz o que consertar, "ocorreu um erro" não.

    Cache — tempest cache¶

    tempest cache ping                       # PONG, ou código 1
tempest cache stats                      # versão, chaves, memória, hit ratio
tempest cache flush --namespace orders   # invalida o que o @cached registrou
tempest cache flush --tag user:42
tempest cache flush --key "cache:orders:list:abc"
tempest cache flush --all --yes          # FLUSHDB

    As opções direcionadas passam pelo CacheInvalidator — o mesmo código que o serviço chama —, então as chaves apagadas aqui são as que o @cached escreveu lá. Passe o mesmo --key-prefix que os decorators usam, senão os registries não batem.

    --all é FLUSHDB, não 'limpar o cache'

    Apaga toda chave do banco selecionado: sessão, contador de rate limit e feature flag junto, quando dividem o mesmo Redis. Por isso exige --yes. Na dúvida, invalide por namespace.

    O hit ratio é do servidor, não da sua aplicação

    keyspace_hits / keyspace_misses são contadores do Redis desde o último restart, somando todos os clientes. O Redis não atribui hit a chamador — o número responde "esse servidor está sendo útil", não "meu endpoint X está".

    Diagnóstico — tempest doctor¶

    O check-config lê as settings e raciocina sobre elas; não abre socket nenhum. Isso é a troca certa para um gate rápido e a errada para "por que o serviço não sobe", cuja resposta quase sempre é uma dependência fora do ar, inalcançável deste host, ou com credencial que ninguém atualizou.

    tempest doctor
tempest doctor --json            # pra script / healthcheck de deploy
tempest doctor --timeout 2       # aperta a espera de cada sonda de rede

    Rotas — tempest routes¶

    Lista as URLs que a aplicação de fato serve.

    tempest routes

    METHOD  PATH                    NAME          SCHEMA  GUARDS
GET     /api/items/{item_id}    read_item     yes     require_admin
POST    /api/items/             create_item   yes     require_admin
GET     /health                 health        yes     -
GET     /painel                 painel        no      -

    Quatro coisas nessa tabela que uma leitura de código não te dá de graça:

    • Router montado aparece. Desde o FastAPI 0.141.1, o include_router guarda uma entrada _IncludedRouter em vez de achatar as rotas na aplicação — então {r.path for r in app.routes} não contém nenhum path do router incluído. O comando lê a mesma expansão que o gerador de OpenAPI percorre.
    • Prefixo já resolvido. O path é o do router mais o de cada include_router acima dele.
    • Rota fora do schema também aparece, com SCHEMA=no — página HTML e endpoint interno servem tráfego, e é justamente o que uma resposta tirada do openapi.json esconde.
    • GUARDS mostra a dependência herdada do include, não só a declarada na rota. É como se confere que o Depends(require_admin) do include_router alcançou tudo que devia.

    Filtros e formato:

    tempest routes --match /api/orders        # só paths com esse trecho
tempest routes --method post,delete       # só esses métodos
tempest routes --all                      # inclui /docs, /redoc, /openapi.json
tempest routes --json                     # array JSON, pra script
tempest routes --app src.server:app       # app fora dos lugares convencionais

    Sem --app, o comando procura o app em src.server:app, src.api.app:create_app, main:app (e os mesmos sob app/). Quando nada resolve, ele lista o que tentou e por quê antes de sair com código 2. --match que não casa com nada sai com código 1, pra typo em script falhar em vez de parecer aplicação sem rota.

    Empacotar uma rota para a IA — tempest bundle-route¶

    Um endpoint deu bug e você quer perguntar pro GPT, pro Gemini ou pro Claude. A pergunta só tem resposta boa se a IA enxergar o caminho inteiro da requisição: o router, a dependência que monta o controller, o controller, o service, o repository, o model e os schemas. Colar isso à mão é abrir oito arquivos — e quase sempre falta justamente aquele onde o bug mora.

    tempest bundle-route monta esse pacote pra você, em markdown:

    tempest new demo
cd demo
cp .env.example .env
tempest bundle-route "GET /api/"

    O começo da saída, medido num projeto recém-gerado:

    # Route bundle: `GET /api/`

- **Method:** `GET`
- **Path:** `/api/`
- **Endpoint:** `index`
- **Dependencies:** `get_service_info_controller`, `get_settings`

## Files (6 files, 277 lines)

| Layer | File | Lines |
| --- | --- | --- |
| router | `src/api/routers/service_info.py` | 30 |
| dependencies | `src/api/dependencies/controllers.py` | 37 |
| controllers | `src/controllers/system/service_info.py` | 40 |
| schemas | `src/schemas/service_info.py` | 23 |
| core | `src/core/settings.py` | 117 |
| other | `src/scripts/composition.py` | 30 |

    Depois da tabela vem cada arquivo inteiro, numa seção ## `caminho` com um bloco python, na mesma ordem. Cole tudo no chat e escreva a pergunta embaixo.

    Num domínio de verdade o pacote cresce do jeito que você espera: com o domínio products que o CLAUDE.md gerado ensina a escrever, tempest bundle-route "GET /api/products" deu 15 arquivos, 635 linhas — router, api/dependencies/controllers.py e resources.py, controller, service, repository, model, schema, core/constants/messages/errors.py, core/exceptions/conflict.py e not_found.py, core/settings.py, db/configs/connection.py e names.py e scripts/composition.py. Nenhum arquivo do service_info.

    O resumo sai em stderr, então o stdout é só o markdown:

    GET /api/: 6 file(s), 277 line(s). The bundle is your source code: review it before pasting it anywhere.

    Como ele acha os arquivos¶

    1. A rota é resolvida no app vivo, pela mesma expansão do tempest routes — prefixo do include_router já aplicado. O ponto de partida é o endpoint e toda a árvore de Depends, inclusive a dependência herdada do include_router.
    2. Daí em diante, tudo é estático. Cada módulo do projeto é lido com ast; nada além do próprio app é importado ou executado.
    3. O caminho é por símbolo, não por módulo. O scaffold manda importar do pacote (from src.services import ProductService), e cada __init__.py re-exporta todos os domínios. Seguir o módulo inteiro puxaria o projeto todo. Em vez disso, o nome é seguido pelo re-export até o arquivo que o define, e só os nomes que aquela definição usa são seguidos depois.
    4. O arquivo entra inteiro assim que uma definição dele é alcançada. É por isso que o api/dependencies/controllers.py aparece com os providers dos outros domínios dentro — mas os controllers desses domínios não. Um __init__.py atravessado só como re-export não entra.

    A ordem é por camada: router, dependencies, controllers, services, repositories, models, schemas, core, e o resto. O arquivo do endpoint vem sempre primeiro.

    O pacote é o seu código-fonte

    O comando só lê arquivos .py dos pacotes do projeto (src/ ou app/) dentro da raiz — nunca o .env, a biblioteca padrão, o site-packages, uma .venv dentro do projeto, nem o próprio SDK. Mas o que ele lê é o seu código, inteiro, e pode ser proprietário. Valor escrito direto no código (um default de Settings, uma chave de teste) vai junto. Releia antes de colar num serviço de terceiro: quem decide onde o código vai é você.

    Escolher a rota¶

    O argumento é "MÉTODO /path", com o path que o tempest routes imprime. O método não diferencia maiúscula de minúscula. Sem método, o path precisa ter um só:

    tempest bundle-route "GET /api/products"
tempest bundle-route /api/                               # só um método serve esse path
tempest bundle-route "get /api/"                         # método em minúscula também vale

    Quando a escolha não é única, o comando para em vez de adivinhar:

    • Path com vários métodos e nenhum nomeado sai com código 2 e lista os métodos: tempest bundle-route /api/products, no domínio da receita, responde error: /api/products is served by several methods: GET, POST. Name one, e.g. 'GET /api/products'.
    • Rota que não existe sai com código 1 e sugere as parecidas:
    error: no route matches 'GET /health'.
  did you mean: GET /health/liveness
  did you mean: GET /health/readiness
  did you mean: GET /api/
  did you mean: GET /redoc
  did you mean: GET /openapi.json
  run `tempest routes` to list every route.
    • Rota servida por código instalado (o /health/liveness do SDK, por exemplo) não alcança nenhum arquivo do projeto e sai com código 1.

    Opções¶

    tempest bundle-route "GET /api/" --output bug.md         # grava no arquivo, stdout vazio
tempest bundle-route "GET /api/" --max-depth 0           # só os arquivos que definem endpoint e dependências
tempest bundle-route "GET /api/" --app src.server:app    # app fora dos lugares convencionais

    --max-depth conta os saltos a partir do endpoint e das dependências. Com 0, a mesma rota GET /api/ cai para 3 arquivos, 184 linhas (router, api/dependencies/controllers.py e core/settings.py, onde mora o get_settings). Sem a opção, tudo que é alcançável entra.

    O app precisa importar

    Como no tempest routes, o comando importa o app do projeto, então o .env (ou as variáveis de ambiente) precisa estar lá — por isso o cp .env.example .env no exemplo. Quando o import falha, ele lista o que tentou e por quê, e sai com código 2.

    Recap¶

    • tempest bundle-route "MÉTODO /path" junta o código de uma rota num markdown pronto pra colar num chat de IA.
    • A rota sai do app vivo; o código é seguido por símbolo, estaticamente, sem atravessar para outros domínios.
    • Só .py do projeto, nunca .env nem pacote instalado — e mesmo assim é o seu código: revise antes de colar.

    Exportar o contrato — tempest openapi-export¶

    O openapi-client consome a spec de outra pessoa; este escreve a sua.

    # Documento no stdout
tempest openapi-export

# Arquivo (JSON por padrão)
tempest openapi-export --out contracts/openapi.json

# YAML (precisa do extra [openapi])
tempest openapi-export --out contracts/openapi.yaml --yaml

    Duas coisas saem disso. A primeira é alimentar um gerador — o próprio tempest openapi-client, um gerador de cliente TypeScript, um mock server — sem subir o serviço. A segunda é commitar o documento e transformar mudança de contrato em algo que o revisor vê:

    tempest openapi-export --out contracts/openapi.json --check

    error: contracts/openapi.json is out of date:
  + DELETE /api/items/{item_id}
  - GET /api/legacy
  ~ /api/items/{item_id} changed
Run 'tempest openapi-export --out <file>' to refresh it.

    Código 1 quando difere, 0 quando está em dia. Operação que entrou e que saiu vêm primeiro porque são as que quebram consumidor; mudança dentro de uma operação vira ~ <path> changed. "A spec mudou" não é mensagem revisável — por isso o comando nomeia o que se moveu.

    Rode --check no mesmo job que roda os testes. O dia em que alguém muda um status code, um campo obrigatório ou um path, o PR fica vermelho com a linha exata, em vez de o cliente descobrir em produção.

    Descrição de PR com IA — tempest pr-prompt¶

    A branch ficou verde e falta a parte que todo mundo pula: escrever a descrição do Pull Request. Qualquer assistente escreve uma boa — o que falta pra ele são as duas coisas que moram no repositório: o template que o time combinou e o diff que a branch realmente produziu.

    tempest pr-prompt monta os dois num prompt só e joga em stdout, então ele pipa direto pra IA que você usa:

    tempest pr-prompt                               # compara com main, prompt no stdout
tempest pr-prompt develop                       # outra base
tempest pr-prompt | claude -p                   # pipa direto pro assistente
tempest pr-prompt --out pr_prompt.txt           # grava num arquivo pra colar

    O prompt carrega três blocos:

    1. O template do PR. O do próprio repositório vence — é o contrato que os revisores daquele projeto leem. São procurados, nessa ordem: .github/pull_request_template.md, .github/PULL_REQUEST_TEMPLATE.md, .github/PULL_REQUEST_TEMPLATE/pull_request_template.md, .gitlab/merge_request_templates/default.md, docs/pull_request_template.md, .pull_request_template.md e pull_request_template.md. Sem nenhum deles, entra o template embutido do SDK.
    2. As regras que impedem a IA de devolver o template com os placeholders dentro: nada de Sim/Não sem escolher, nada de _texto em itálico_ de instrução, nenhuma seção apagada, e nada de inventar migration, env var ou dependência que não aparece no diff.
    3. O contexto da branch: assuntos dos commits, a lista --name-status dos arquivos alterados e um trecho do patch de cada arquivo.

    O diff é o mesmo que a forge mostra

    Os patches são lidos como base...head (três pontos) — o diff em relação ao merge-base, que é o que o GitHub/GitLab exibe no PR. Com dois pontos, todo commit que entrou na base depois que sua branch nasceu seria atribuído a você.

    O que é completo e o que é amostrado

    A lista de commits e a lista de arquivos alterados vão inteiras, sempre — a IA sempre sabe o que mudou. O que é limitado são os trechos de diff: por padrão os 10 arquivos com mais linhas alteradas, cada um cortado em 1500 caracteres. Ou seja, o que é amostrado é como mudou.

    Os trechos são limitados porque o diff inteiro de uma branch grande não cabe no contexto e é quase todo ruído (lock file, changelog, migration gerada). Os arquivos entram ordenados por linhas alteradas, não em ordem alfabética — senão o orçamento vai embora em .github/ e CHANGELOG.md antes de chegar no arquivo sobre o qual o PR é:

    tempest pr-prompt --full                        # todos os arquivos, patch inteiro
tempest pr-prompt --max-files 20                # 20 arquivos com patch (default: 10)
tempest pr-prompt --max-files 0                 # só a lista de arquivos, sem patch
tempest pr-prompt --max-chars 4000              # mais patch por arquivo (default: 1500)

    --full levanta os dois limites de uma vez — use numa branch pequena o bastante pra mandar inteira. Ele recusa vir junto com --max-files / --max-chars (saída 2): sobrescrever em silêncio um número que você digitou seria pior que reclamar.

    Nada é cortado em silêncio

    Um patch truncado leva a marca trecho cortado e os arquivos que ficaram sem trecho viram uma linha explícita no prompt (Mais N arquivo(s) alterado(s)…). A IA lê um contexto parcial como parcial, em vez de tratar o pedaço como a mudança inteira. O corte também respeita a quebra de linha, pra não sobrar meia linha de diff — que a IA leria como código que não existe.

    O resumo (template escolhido, contagem de commits/arquivos) sai em stderr, então o pipe continua limpo:

    template: .github/pull_request_template.md
7 commit(s), 12 changed file(s), 10 excerpt(s), 2 file(s) without a patch.

    Outras opções:

    tempest pr-prompt --head feat/outra             # descreve outra branch, sem checkout
tempest pr-prompt --lang en                     # regras e template embutido em inglês
tempest pr-prompt -t docs/meu_template.md       # template explícito, vence todos
tempest pr-prompt -p ../outro-repo              # roda contra outro repositório

    Base inexistente vira origin/<base>

    Num clone recém-feito costuma não existir uma main local, só origin/main. Quando a base não resolve, o comando tenta origin/<base> antes de falhar. Se nem isso existir, ele sai com código 2 e diz qual ref não encontrou. Quando a comparação não tem nem commit nem arquivo, a saída é código 1 — quase sempre a base está errada.

    Gates de qualidade¶

    Esses comandos vêm do tempest-cli (v0.226.0)

    O gate de qualidade não tem nada de FastAPI — é ruff, mypy e pytest. Desde a v0.226.0 ele vive num pacote próprio, tempest-cli, que o extra [cli] do SDK declara e que o SDK monta na CLI dele.

    Nada muda para você: tempest check é o mesmo comando, com as mesmas flags e o mesmo [tool.tempest] typing_strictness. O que muda é que quem não usa FastAPI agora consegue instalar só o gate:

    uv add --dev tempest-cli
tempest-cli check

    Por que separar: para chegar nesses quatro comandos era preciso instalar FastAPI, SQLAlchemy, Alembic e Pydantic — 38,7 MB de dependências e cerca de 0,5 s de import por invocação, medidos, para comandos que não tocam em nada disso.

    Os dois nunca divergem porque há uma implementação só: o SDK chama register_commands(app) do tempest_cli. Importar tempest_fastapi_sdk.cli.lint ou .pr_prompt continua funcionando e devolve as mesmas funções.

    Os comandos de lint chamam a ferramenta do projeto, procurando o executável nesta ordem:

    1. o $VIRTUAL_ENV ativado;
    2. o .venv mais próximo, subindo a partir do diretório atual — o ambiente do projeto, mesmo sem ativação;
    3. o diretório do interpretador que roda o próprio tempest;
    4. o PATH, pulando shim de gerenciador de versão (pyenv/asdf) que não despacha para lugar nenhum;
    5. uv run --with <tool> <tool>, quando o uv está no PATH.

    O projeto vem antes do ambiente da CLI de propósito: com uv tool install, a CLI tem o próprio ruff, e um projeto que fixa outra versão continua rodando a que fixou.

    tempest lint                                    # ruff check .

tempest fix --unsafe                            # também aplica os --unsafe-fixes do ruff

tempest fmt-check                               # ruff format --check .   (somente leitura)

    test e check rodam a suíte em paralelo por padrão desde o tempest-cli 0.6.0 (o extra [cli] declara tempest-cli>=0.7.0); sem o pytest-xdist no ambiente do pytest, avisam e rodam em série. Quando usar, o banco por worker e o que fazer com teste que só falha em paralelo estão na receita de testes.

    tempest fix é a passada única de "organize o projeto" — ordena e remove imports duplicados, descarta imports não usados, normaliza aspas de strings, remove espaços em branco no fim das linhas e então roda ruff format para alinhar indentação, comprimento de linha, linhas em branco e a quebra de linha final. Rode-o antes do push quando o CI fica pegando detalhes de estilo.

    O relatório sai do arquivo já formatado (tempest-cli 0.5.1)

    O tempest fix roda três passadas: ruff check --fix-only, ruff format e, por fim, ruff check, que é de onde saem o relatório e o exit code. Uma violação que o formatter resolveu não aparece mais nem derruba o comando. O que sobra depois da formatação continua saindo com código ≠ 0, então o CI segue falhando nas pendências reais.

    Comentários e strings longos são encurtados, com prova de AST (tempest-cli 0.5.1)

    O ruff format não quebra comentário nem string literal — igual ao Black.     Os passos do SDK no tempest check¶

    O tempest check vem do tempest-cli, que não sabe nada de FastAPI. O SDK entrega a ele três passos próprios, que rodam depois do mypy e antes do pytest, nesta ordem, com o mesmo contrato dos outros: o primeiro exit code diferente de zero para o gate.

    Settings obrigatório no lint-schemas¶

    O lint-schemas importa o src.schemas num processo filho com ENV=test quando o shell não define ENV — e, com ENV=test, o EnvironmentSettings descarta o .env. Um Settings com campo obrigatório sem default (um segredo como ADMIN_SECRET_KEY, que não deve ter placeholder) não importa, e o passo sai com 2. Depois do traceback vem o motivo:

    Dê ao filho o que ele precisa, só para este passo:

    [tool.tempest]
lint_schemas_env = { ADMIN_SECRET_KEY = "lint-only" }

    A precedência é: o default ENV=test, depois a tabela, depois o shell — um valor que o shell exporta nunca é trocado pelo placeholder. Valor que não é string sai com 2.

    Router: controller por Depends, resposta em schema¶

    As duas regras de routers/ cobrem os desvios que mais aparecem num router: montar o controller na mão dentro da rota e devolver a linha ORM. Este router, escrito num projeto do tempest new, faz os dois:

    O que as regras de router não veem

    Elas leem sintaxe e nunca importam o projeto, então ficam de fora: rota sem anotação de retorno e sem response_model=; model guardado fora de qualquer models/ e importado de módulo sem esse segmento; as bases ORM do próprio SDK (BaseUserModel) usadas direto na rota; controller montado por alias (factory = ProductController; factory()) ou classe cujo nome não termina em Controller / Service.

    Task, consumer, agente e seed não têm Depends. Em vez de cada classe ganhar um from_session, junte as funções build_* num composition root e reutilize-o em todos esses lugares e na suíte. A receita de agentes com banco mostra a forma.

    Quando o pacote fecharia ciclo

    Às vezes o import pelo pacote da camada fecha um ciclo: no transport, task e script importavam api.dependencies.resources direto, porque importar o pacote api.dependencies fecharia ciclo com src.tasks. Esse é o caso da exceção declarada ("IMP002 <caminho>::<nome>": "<motivo>"), não de reescrever o import.

    Quando o valor sorteado quebra o pytest -n

    Cada worker do pytest-xdist importa o módulo por conta própria. Se o id do teste depende de um valor sorteado, cada worker coleta ids diferentes e a execução aborta com "Different tests were collected". Medido com pytest -n 2: random.randint(), time.time(), secrets.token_hex(), os.urandom(), str(uuid4()), uuid4().hex, f"{uuid4()}" e pytest.param(..., id=str(uuid4())) abortam. Um uuid4() ou datetime.now() cru passa — o pytest dá a esses objetos o id pela posição (v0, v1) —, e por isso o TST004 só os acusa quando viram texto ou entram em ids= / id=.

    Aviso, erro e exceção declarada¶

    Toda regra tem uma severidade. Erro derruba o passo (exit code 1); aviso sai com (warning) depois do código e não derruba. Regra nova entra como aviso numa release e vira erro na seguinte — assim um serviço existente tem uma release inteira para migrar. Para migrar uma regra por vez, selecione-a com --rule (repetível, aceita minúsculas):

    tempest lint-layers --rule SVC002              # só uma regra
tempest lint-layers --rule SVC002 --rule RTR001
tempest lint-layers --strict                   # aviso também derruba

    O tempest check roda o passo sem --rule. Para o gate derrubar em aviso também, ligue no pyproject.toml — o --strict/--no-strict da linha de comando vence a config:

    [tool.tempest]
layers_strict = true

    Exceção que o projeto assume fica num lugar só, com motivo, revisada no diff como código: o dict ARCHITECTURE_EXCEPTIONS em tests/architecture_exceptions.py. A chave é "<CÓDIGO> <caminho>" (todas as violações daquele código no arquivo) ou "<CÓDIGO> <caminho>::<alvo>" (só a que fala daquele nome — a classe, Classe.método ou a função). O caminho é relativo à raiz do projeto. O arquivo também é lido com ast, nunca importado:

    """Exceções de arquitetura que o projeto assume, cada uma com motivo."""

ARCHITECTURE_EXCEPTIONS: dict[str, str] = {
    "SVC001 src/services/catalogue/catalogue.py::CatalogueService": (
        "catálogo estático, sem repository para o BaseService"
    ),
    "REPO001 src/db/repositories/legacy/legacy.py": "wrapper mantido até a 2.0",
}

    Com esse arquivo, um src/services/catalogue/catalogue.py que define CatalogueService (sem BaseService) e uma função de módulo load_items, e nenhum legacy.py, o tempest lint-layers sai assim (saída real, exit code 1 por causa do SVC002):

    O SVC001 do CatalogueService sumiu, porque a exceção o cobre. A entrada de REPO001 não casa com nada e vira o aviso EXC002: exceção não sobrevive ao código que ela desculpava.

    Código Severidade O que acusa
    EXC001 erro, sempre (mesmo com --rule) entrada que o checker não consegue usar: chave fora da forma, código desconhecido, motivo vazio ou que não é string literal, chave repetida, arquivo sem o dict

    Marcador ou exceção declarada?

    Os marcadores # tempest: no-base-service e # tempest: router-builds continuam valendo. A exceção declarada serve para qualquer regra, inclusive as que não têm marcador, e junta num arquivo só o que antes ficava espalhado — a review lê o motivo de todas de uma vez.

    Metadado de schema — tempest lint-schemas¶

    O cliente lê o openapi.json, e um campo sem title, description e examples chega lá só com nome e tipo. Essa regra não sai de ast: o metadado só existe depois que o Pydantic montou o modelo. Por isso ela importa o pacote de schemas (src.schemas, ou app.schemas), em vez de ler o código como o lint-layers:

    # src/schemas/order.py
from pydantic import Field
from tempest_fastapi_sdk import BaseSchema


class AddressSchema(BaseSchema):
    """Endereço de entrega."""

    city: str = Field(title="Cidade", description="Cidade da entrega.")


class OrderCreateSchema(BaseSchema):
    """Pedido novo."""

    total_cents: int
    address: AddressSchema = Field(title="Endereço", description="Onde entregar.")

    tempest lint-schemas (com src/schemas/__init__.py exportando os dois; saída real, exit code 1):

    src.schemas.order.AddressSchema.city: missing examples
src.schemas.order.OrderCreateSchema.total_cents: missing title, description, examples
2 schema field(s) without documentation.
    • O campo folha (um valor: str, int, enum, list[str]) precisa dos três. O campo que guarda outro schema (AddressSchema, list[ItemSchema], ItemSchema | None) precisa só de title e description — os exemplos são os do schema de dentro. Por isso o address passa.
    • Cada campo sai uma vez, na classe que o declara, mesmo herdado por vários schemas exportados. Os campos que o BaseResponseSchema traz (id, created_at...) já vêm documentados.
    • Título em branco e examples=[] contam como ausentes. Pacote que não importa sai com exit code 2 e o traceback.

    O mesmo check roda dentro da suíte, que é como o projeto do tempest new o cobra a cada tempest check — o scaffold já traz este teste:
