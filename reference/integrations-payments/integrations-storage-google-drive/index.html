    tempest_fastapi_sdk.integrations.storage.google_drive¶

    Google Drive como backend de UploadUtils: upload para uma pasta compartilhada.

    « Integrações e pagamentos

    storage ¶

    Google Drive as an :class:~tempest_fastapi_sdk.utils.UploadStorage backend.

    Drive addresses files by id, not by path, and two files in one folder may share a name. So the key an :class:~tempest_fastapi_sdk.utils.UploadUtils hands the backend is stored in the file's appProperties (private to this app) under :data:TEMPEST_KEY_PROPERTY, and every lookup searches that property inside the configured folder::

    '<folder>' in parents
and appProperties has { key='tempest_key' and value='<key>' }
and trashed = false

    The file's name is only for people browsing the folder: the last segment of the key.

    Writing a key that already exists replaces the content of that file — same id, same link, new media (files.update) — instead of creating a second file, matching what the local and MinIO backends do with an existing key. Two writes racing on a brand-new key can still both create a file: Drive has no conditional create. :meth:GoogleDriveUploadStorage.exists then answers True, :meth:GoogleDriveUploadStorage.delete removes every match, and the next write replaces the first match.

    TEMPEST_KEY_PROPERTY module-attribute ¶

    TEMPEST_KEY_PROPERTY: str = 'tempest_key'

    The appProperties key that holds the UploadStorage key.

    APP_PROPERTY_MAX_BYTES module-attribute ¶

    APP_PROPERTY_MAX_BYTES: int = 124

    Drive's documented ceiling for one property, key plus value, in UTF-8.

    From "Add custom file properties" (https://developers.google.com/workspace/drive/api/guides/properties). Enforced here so a long key fails before any byte is sent instead of at the API; not measured against the live service.

    :class:~tempest_fastapi_sdk.utils.UploadStorage on a Google Drive folder.

    Plug it into :class:~tempest_fastapi_sdk.utils.UploadUtils unchanged::

    **settings.google_drive_kwargs()

    presigned_url async ¶

    presigned_url(key: str, *, expires: timedelta = timedelta(hours=1)) -> str | None

    Refuse: Google Drive has no presigned URLs.

    Drive serves a file to callers holding a Drive permission; there is no temporary signed link to mint, and returning the permanent webViewLink here would let a caller treat it as one that expires.     client ¶

    An async client for the Drive API v3 calls an upload backend needs.

    Five calls, each written from Google's reference (https://developers.google.com/workspace/drive/api/reference/rest/v3/files): files.list, files.get, files.delete, and files.create / files.update through the resumable upload protocol (https://developers.google.com/workspace/drive/api/guides/manage-uploads#resumable).

    Every call sends supportsAllDrives=true, so a folder inside a Shared Drive behaves like one in My Drive.

    The resumable upload streams in pieces of a multiple of 256 KiB (the protocol's granularity). Each piece that is not the last says Content-Range: bytes <first>-<last>/*; the server answers 308 Resume Incomplete with a Range: bytes=0-<n> header naming what it kept, and the next piece starts right after it, so bytes the server did not keep are re-sent and nothing else is. The client reads one piece ahead, so the last PUT always carries bytes and the total — a payload that is an exact multiple of the piece size never ends on an empty bytes */<total>, which the protocol also uses as a status query. The only empty closing PUT is the zero-byte file's bytes */0.

    A 429/5xx, a 403 whose reason is rateLimitExceeded or userRateLimitExceeded, or a transport error is retried with exponential backoff — or after the Retry-After seconds of a 429/503, capped at backoff_max_seconds — up to max_retries times. On a piece, the client first asks the session how much it holds (Content-Range: bytes */<total or *>); the stream already sent is never replayed. A 404 on a piece or a status query means the session itself is gone (reason :data:UPLOAD_SESSION_NOT_FOUND_REASON).

    upload async ¶

    upload(
    chunks: AsyncIterator[bytes],
    *,
    metadata: Mapping[str, object],
    content_type: str,
    file_id: str | None = None,
) -> GoogleDriveFile

    Stream chunks through a resumable session.

    The first piece is read from chunks before the session is opened, so an iterator that raises on its first chunk (a content validator) leaves nothing behind on Drive. Google's upload guide describes the file as created when the session completes, so an exception raised by chunks mid-stream, which abandons the session before its last piece, is expected to leave no file — not measured against the live service. When the upload fails, chunks is closed (aclose) if it is an async generator.

    The stream is read one piece ahead: a piece goes out with /* only while more bytes are known to follow, so the last PUT always carries bytes and the total. The zero-byte file is the exception — it is closed with an empty bytes */0.

    A 308 naming fewer bytes than were sent re-sends the missing ones; one that names no progress at all waits the backoff before re-sending, and gives up as upload_stalled after max_retries such answers in a row. A 308 naming fewer bytes than the client already dropped from its buffer cannot be recovered and is raised at once as upload_range_regressed.

    auth ¶

    Service-account access tokens for the Google Drive API.

    A service account authenticates with the OAuth 2.0 JWT bearer grant (RFC 7523), described by Google in "Using OAuth 2.0 for Server to Server Applications" (https://developers.google.com/identity/protocols/oauth2/service-account): the server signs a JWT with the account's private key (RS256), posts it to the token endpoint and receives a short-lived access token.

    No google-auth here: the whole exchange is one signed JWT and one form post, built on pyjwt + cryptography (both already floors of the [auth]/[oidc] extras) and httpx.

    The token exchange sits behind :class:AccessTokenProvider, so a provider for a user's OAuth token can replace :class:ServiceAccountTokenProvider without touching :class:~tempest_fastapi_sdk.integrations.storage.google_drive.GoogleDriveClient.

    ServiceAccountTokenProvider ¶

    ServiceAccountTokenProvider(
    credentials: ServiceAccountCredentials,
    *,
    http_client: AsyncClient,
    scopes: Sequence[str] = (DRIVE_SCOPE,),
    refresh_margin_seconds: float = TOKEN_REFRESH_MARGIN_SECONDS,
    clock: Callable[[], float] = time,
)

    Access tokens from a service account, via the JWT bearer grant.

    Each exchange signs a fresh assertion with claims iss (client_email), scope (space-separated), aud (token_uri), iat and exp (iat + one hour), RS256, with kid set to private_key_id. The token is cached until :data:TOKEN_REFRESH_MARGIN_SECONDS before its expires_in, and an :class:asyncio.Lock makes concurrent callers share one exchange instead of each running their own.

    Neither the assertion, the private key nor the access token is ever logged or put in an exception message.
