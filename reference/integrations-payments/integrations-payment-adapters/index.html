    create_pix_charge async ¶

    create_pix_charge(request: PixChargeRequest) -> PixCharge

    Create a charge at OpenPix.

    amount_cents goes across unchanged: OpenPix states value in cents already, and since v0.259.0 the generated model types it as int. The response still goes back through to_cents, which now narrows nothing and validates everything — a value that is negative or not whole means the assumption about the field is wrong, and that is worth an error rather than a plausible number.

    expires_in is sent in seconds, truncated to a whole one: the field is an integer count, and timedelta.total_seconds() answers a float. OpenPix refuses anything under five minutes with a 400; that floor is not re-checked here, because duplicating a provider's validation is how the copy drifts from the original.

    The create is idempotent on reference: it goes out with ?return_existing=true, so a retry after a timeout — when the first request may have landed — answers the charge that already exists for that correlationID, as Woovi's specification describes the parameter (not measured against the sandbox). That is the same guarantee the Mercado Pago adapter gives through X-Idempotency-Key, and the one the protocol documents for :attr:PixChargeRequest.reference.

    refund_pix_charge async ¶

    refund_pix_charge(
    charge_id: str, amount_cents: int | None = None, *, refund_reference: str
) -> PixRefund

    Refund a paid charge, idempotently on refund_reference.

    OpenPix keys a charge refund by a correlationID of the caller's and lists the charge's refunds with it (GET /api/v1/charge/{id}/refund), so idempotency is checked here rather than trusted to the provider: the charge's refunds are read first, and a refund already carrying refund_reference is answered as it is, without a second POST. Whether OpenPix itself refuses a repeated refund correlationID is not documented in its specification and was not measured; what is guaranteed is the read before the write, and the read after a failed write: when the POST raises, the refunds are read again and a refund carrying the reference is answered instead of the error — the answer was lost, not the refund. Two calls racing on the same reference can still both reach the POST; the recipe serializes per reference.

    The charge is read first because the refund route is addressed by the charge's correlationID (the route's id parameter, per the specification) while :attr:PixCharge.provider_charge_id is OpenPix's own id. The amount always goes out explicit — what is left, for a full refund — so a retry carries the same body.

    OpenPixPayoutProvider ¶

    OpenPixPayoutProvider(http: HTTPClient)

    OpenPix as a :class:~...payment.base.PayoutProvider.

    Sends with autoApprove: true: one call creates and approves the payment. The two-step form (create, then approve) leaves a window in which a payment exists but is not approved, and a crash inside that window is a payout nobody knows whether to retry. Reading the answer depends on v0.304.0's overlay fix, which lets Payment.status carry the "APPROVED" that the autoApproved response documents.

    Error mapping (the contract the wallet relies on):

    • HTTP 4xx, or a payment answered DENIED/FAILED -> :class:~tempest_fastapi_sdk.exceptions.PayoutRejectedException;
    • anything else that goes wrong — HTTP 5xx, timeout, connection error, a body that does not validate — propagates unchanged, because the payment may have been made.

    Attributes:

    Name Type Description
    provider_name str

    Always "openpix".

    Build the provider over a transport that never re-sends.

    Takes the HTTPClient rather than an OpenPixClient so it can check the one setting that decides whether a payout can be paid twice. HTTPClient retries every method, POST included, on HTTP 429/5xx and on a read timeout — measured with the default policy: one POST answered 500 goes out three times. For a payout that is the worst case: the first request may have created the payment, and the retry gets an answer the adapter would report as a refusal, so the wallet would give back money that already left.

    Parameters:

    Name Type Description Default
    http HTTPClient

    Transport carrying the AppID, pointed at the right environment, built with retry_policy=RetryPolicy(max_attempts=1).

    		 required

    Raises:

    Type Description
    ValueError

    If http would retry a request.

    Two forms, told apart by refund_reference:

    • With it — the :class:~...payment.base.PixRefundProvider form. The X-Idempotency-Key is derived from the order id and the reference (:func:_refund_idempotency_key), so repeating the call replays the refund instead of applying it twice. The order is read first: asking for more than is left raises :class:~tempest_fastapi_sdk.exceptions.PixRefundExceedsBalanceException — after the request still goes out under the derived key, so a retry of a refund that already landed (which is why nothing is left) gets the provider's replay instead of the exception. Returns a :class:PixRefund.
    • Without it — the form this method had before the refund contract existed, kept unchanged: a fresh key per call (retries of that one call are still safe, a second call is a second refund), no balance check, and a :class:PixCharge back.

    Mercado Pago's refund entries carry no reference of the caller's, so the refund this call made is read as the last entry of the action's answer — in the sandbox fixtures the answer lists every refund of the order, oldest first (pix_refund_rest.json). That a replayed answer is byte-for-byte the first one was measured on the create (vendor/mercadopago-evidence.md section 9.6), not on the refund route.

    client: AsyncClient | None = None,
    timeout: float = 10.0,
)

    Move an order and deliver the signed webhook announcing it.

    Where the delivery goes:

    • app and webhook_url — in process, through the whole application (middleware, the signature check, the service's handler) over httpx.ASGITransport. webhook_url is a path ("/api/webhook/mercadopago", sent to http://localhost) or an absolute URL whose host the app accepts.
    • webhook_url alone — over the network, to a running service ("http://api:8000/api/webhook/mercadopago"), with client or a short-lived client per call.
    • neither — only :meth:apply_to delivers; the development routes use it with the request's own application.
