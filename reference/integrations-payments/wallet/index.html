    tempest_fastapi_sdk.wallet¶

    Carteira: saldo, extrato, retenções e saque Pix em centavos inteiros.

    « Integrações e pagamentos

    wallet ¶

    Wallet module — balance, ledger, holds and Pix withdrawals in integer cents.

    Reusable building blocks over the SDK primitives: a balance column mixin and an abstract ledger table with a make_* factory, a :class:WalletService whose every balance change is one SQL UPDATE plus its ledger line in the same transaction, a withdrawal that debits before it pays and gives the money back only when the provider refused, :func:claim_once for settlements that must run once, fee and split arithmetic in basis points, and an opt-in :func:make_wallet_router.

    The decisions that go wrong the same way in every product, and are made here once:

    • a balance read in Python and written back loses credits under concurrency — the service never does that;
    • a hold checked before the debit can be drained by two withdrawals at once — the hold is part of the debit's WHERE;
    • a payout that failed ambiguously must keep its debit — returning it could pay twice;
    • money is never a float.

    WalletLedger ¶

    WalletLedger(
    *,
    balances: BaseRepository[Any],
    entries: BaseRepository[Any],
    balance_attribute: str = "wallet_cents",
)

    Credit, debit, reverse and read wallets backed by a ledger.

    Both repositories must share one session: a balance update and its ledger line commit together or not at all. Each move opens entries.transaction(), which is re-entrant: inside a caller's :func:~tempest_fastapi_sdk.db.transaction.transaction block it joins that block and does not commit on its own, so the move and the caller's own writes commit together when the outer block exits — or roll back together when it raises.

    ManualPayoutProvider ¶

    ManualPayoutProvider(
    mailer: AdminMailer,
    *,
    admin_emails: Sequence[str],
    provider_name: str = MANUAL_PAYOUT_PROVIDER,
    subject_prefix: str = "[Saque manual]",
    records: BaseRepository[Any] | None = None,
    record_url: str | None = None,
    hooks: ManualPayoutHooks | None = None,
)

    Pay a withdrawal out by e-mailing the administrators the Pix to send.

    Error contract, as :class:~tempest_fastapi_sdk.integrations.payment.PayoutProvider asks:

    • the mailer raises :class:~tempest_fastapi_sdk.exceptions.EmailDeliveryException or :class:~tempest_fastapi_sdk.exceptions.IntegrationDisabledException -> :class:~tempest_fastapi_sdk.exceptions.PayoutRejectedException. No administrator received the order, so no one will send the money, and the wallet gets its debit back. EmailUtils raises the first one for every SMTP transport failure, including a timeout; a server that accepted the message and then lost the connection is the one case where that is wrong, and the correlation id in the next attempt's e-mail is what reconciles it;
    • anything else propagates, and the wallet keeps the debit and logs it CRITICAL — the outcome is unknown.

    The e-mail carries the whole Pix key, because a person has to type it. The log line names it masked (:func:mask_pix_key).

    With records, every payout is also written as a :class:~tempest_fastapi_sdk.wallet.BaseManualPayoutModel row (PENDING) before the e-mail goes out — the wallet debit has already committed by then. A row that cannot be written refuses the payout (the debit comes back and no e-mail is sent); an e-mail that fails turns the row CANCELED before the refusal. So a debit the wallet keeps always has a row the panel shows, except when the process dies between the debit's commit and this write — the WITHDRAW ledger line, whose reference_id is the correlation id, is what reconciles that case.

    hooks (:class:~tempest_fastapi_sdk.wallet.ManualPayoutHooks) runs on_requested in the transaction that writes the row, and on_canceled in the one that cancels it. An on_requested that raises counts as a row that cannot be written (the payout is refused and the debit returned); an on_canceled that raises leaves the row PENDING and the debit held, and the withdrawal answers :class:~tempest_fastapi_sdk.exceptions.PayoutUncertainException. Settling the row afterwards is :class:~tempest_fastapi_sdk.wallet.ManualPayoutService's job.

    Name Type Description

    ManualPayoutHook ¶

    Bases: Protocol

    A callback run inside a manual payout's transition.

    It receives the session the transition runs on and the row as it is after the transition. Whatever it writes on that session commits with the transition; if it raises, the transition, the refund and its own writes roll back together. Parameters are positional-only so an implementation may name them anything.

    Pay a wallet out to a Pix key: debit first, then transfer.

    The order is the safety property. The debit commits before the provider is called, so a second withdrawal racing this one sees the reduced balance. Then:

    • the provider refuses (:class:~tempest_fastapi_sdk.exceptions.PayoutRejectedException) -> the debit is given back as a WITHDRAW_REFUND line, and the exception is re-raised;

    The platform takes platform_bps of the gross total, rounded down. The gateway fee comes off next. What remains is the net, and every entry of shares_bps takes its basis points of the net, rounded down. residual_recipient takes the rest of the net, so the rounding of every share lands on one known payee instead of disappearing — the rule alofans-api uses for the producer (get_producer_profit), and the only payee transport-backend has (the driver, with no shares_bps).

    claim_once async ¶

    claim_once(session: AsyncSession, model: type[Any], row_id: UUID, column: str) -> bool

    Stamp column with now, only if it is still NULL.

    The guard that makes a settlement run once: UPDATE ... WHERE id = :id AND column IS NULL. Two concurrent callers (a webhook retry and a manual confirmation, say) both issue it; only one finds the column still empty. The loser gets False and must not repeat the effects.

    It does not commit. Call it inside the same :func:~tempest_fastapi_sdk.db.transaction.transaction block as the effects it guards, so a failure in those effects rolls the claim back too.
