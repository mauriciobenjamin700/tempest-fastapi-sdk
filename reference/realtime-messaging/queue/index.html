    tempest_fastapi_sdk.queue¶

    Fila de mensagens sobre o FastStream: publisher, consumer, topologia, retry, dedup e tracing.

    « Tempo real e mensageria

    queue ¶

    FastStream-backed message queue primitives.

    Imports the optional faststream package lazily so the rest of the SDK remains importable when the [queue] extra is not installed.

    MessageBroker is the recommended typed, transport-agnostic facade (constructors, @on / class-based consumers, channel-first publish). AsyncQueueManager is a minimal lifecycle wrapper around an injected broker (renamed from AsyncBrokerManager, kept as a deprecated alias).

    PublishResult ¶

    PublishResult = object

    Transport-specific confirmation returned by publish (or None).

    Each FastStream transport returns its own confirmation type (AMQP ConfirmationFrameType | None, Kafka RecordMetadata or future, NATS PubAck | None, Redis int | bytes).

    MessageBroker ¶

    MessageBroker(broker: BrokerUsecase[Any, Any], *, declare_topology: bool = True)

    Typed, transport-agnostic publish/subscribe over FastStream.

    A message broker is for event-driven fan-out between services or workers: a producer :meth:publish-es an event to a channel and every consumer subscribed to that channel (via :meth:on) receives it. Delivery is at-least-once, so handlers should be idempotent.

    Pick the transport with a constructor rather than importing FastStream yourself::

    from pydantic import BaseModel
from tempest_fastapi_sdk.queue import MessageBroker

mq = MessageBroker.rabbitmq("amqp://guest:guest@localhost:5672/")

class OrderPaid(BaseModel):
    order_id: str

@mq.on("orders.paid")
async def handle(event: OrderPaid) -> None:
    await mark_paid(event.order_id)

# FastAPI lifespan
await mq.connect()
await mq.publish("orders.paid", OrderPaid(order_id="abc"))
await mq.disconnect()

    The handler's type hint (event: OrderPaid) drives decoding: FastStream validates the inbound payload into that Pydantic model before your function runs, so a malformed message never reaches your code. :meth:publish accepts a Pydantic model, a dict, str or bytes — models are serialized to JSON automatically.

    Wrap an already-constructed FastStream broker.

    Prefer the transport constructors (:meth:rabbitmq, :meth:redis, :meth:kafka, :meth:nats); use this directly only to inject a pre-configured or custom broker (e.g. a test broker).

    kafka classmethod ¶

    kafka(
    *bootstrap_servers: str, declare_topology: bool = True, **options: Any
) -> MessageBroker

    Build a Kafka-backed broker ([queue-kafka] extra).

    Kafka has no queues: a channel is a topic, and who gets a copy is decided by the consumer group. Consumers sharing a group_id (see :meth:on) split the topic's partitions between them; each distinct group reads every record. Without a group there is nowhere to commit an offset. A publish key (see :meth:publish) picks the partition, so the records of one key are read in the order they were written.

    on ¶

    on(
    channel: str | QueueSpec,
    /,
    *,
    prefetch: int | None = None,
    ack_policy: AckPolicy | None = None,
    group_id: str | None = None,
    auto_offset_reset: OffsetResetEnum | str | None = None,
    **options: Any,
) -> Callable[[Handler], Handler]

    Register the decorated async function as a consumer of channel.

    The handler's parameter type hint drives decoding — annotate it with a Pydantic model and FastStream validates every inbound message into that model before the handler runs::

    @mq.on("orders.paid")
async def handle(event: OrderPaid) -> None:
    ...

    Parameters:

    Name Type Description Default
    channel str | QueueSpec

    The logical channel to subscribe to. Maps to a queue (RabbitMQ), topic (Kafka), subject (NATS) or channel (Redis) under the hood. A spec with a :class:~tempest_fastapi_sdk.queue.ExchangeBinding (see :meth:QueueSpec.consumer <tempest_fastapi_sdk.queue.QueueSpec.consumer>) declares its exchange and binds the queue to it.

    		 required
    prefetch int | None

    Caps how many unacknowledged messages the broker pushes to this consumer, overriding the connection-wide cap set on :meth:rabbitmq. RabbitMQ only: raises on Kafka, NATS and Redis.

    		 None
    ack_policy AckPolicy | None

    FastStream's ack policy for this consumer. None keeps FastStream's choice, except on a spec with a dead-letter exchange, where it is pinned to REJECT_ON_ERROR so a raising handler's message reaches the dead-letter queue — no faststream import needed. On Kafka the policy is the commit behavior: None is FastStream's ACK_FIRST, offsets auto-committed on a timer whatever the handler did; ACK commits after the handler, also when it raised; NACK_ON_ERROR seeks back to the failed record so it is read again. Any policy but ACK_FIRST needs group_id.

    		 None
    group_id str | None

    Kafka consumer group. Consumers sharing it split the topic's partitions — each record goes to one of them; every distinct group gets its own copy. Kafka only.

    		 None
    auto_offset_reset OffsetResetEnum | str | None

    Where the group starts when it has no committed offset. A member or its value ("earliest", what FastStream's own keyword takes); an unknown value raises ValueError. None keeps Kafka's LATEST. Kafka only.

    		 None
    **options Any

    Extra transport-specific subscriber options forwarded to FastStream (e.g. exchange= on RabbitMQ).

    		 {}

    Returns:

    Type Description
    Callable[[Handler], Handler]

    Callable[[Handler], Handler]: The subscriber decorator.

    Raises:

    Type Description
    ValueError

    When the spec has a dead-letter exchange and ack_policy is ACK, ACK_FIRST or NACK_ON_ERROR, none of which ever dead-letters; or, on Kafka, when the ack policy commits and no group_id is set.
    UnsupportedTopologyError

    When prefetch is set on a transport without it, or group_id / auto_offset_reset on one other than Kafka.

    replay_dead_letters async ¶

    replay_dead_letters(
    source: QueueSpec | RetryTopology | str,
    *,
    into: str | None = None,
    limit: int = DEFAULT_REPLAY_LIMIT,
) -> int

    Move dead-lettered messages back to the queue they failed on.

    For after the fix: each message is read from the dead-letter queue, republished straight to the origin queue through the default exchange — never to the shared exchange, which would hand a second copy to every other consumer of the event — and only then acknowledged. A publish that fails puts the message back on the dead-letter queue and stops the run, so a message is never acknowledged without having been delivered somewhere. The origin queue is checked first: through the default exchange, a publish to a queue that does not exist raises nothing — the broker hands the message back as unroutable — and acking after it would lose it.

    What travels: the body as bytes, message_id (the deduplication key, so a consumer with :meth:deduplicate still recognises it), content_type, content_encoding, correlation_id, priority, timestamp, type, reply_to and the headers, persisted. expiration, app_id and user_id do not: a replay is a new delivery, not a resurrection of the old one's lifetime; FastStream's publish takes no app_id; and the broker checks user_id against the replaying connection's login, so the original's would be refused. The broker's x-death bookkeeping is dropped: the retry middleware counts attempts from it, and a replayed message that kept it would be given up on at its first failure instead of getting a fresh budget.

    At least once, not exactly once: when the publish succeeds and the ack that follows fails (the connection drops between them), the message is both back on the origin queue and still on the dead-letter queue, and the next replay delivers it again. A consumer with :meth:deduplicate skips the second copy by its message_id.

    AsyncQueueManager(broker: BrokerUsecase[Any, Any])

    Manage the lifecycle of an injected FastStream broker.

    A minimal wrapper: it wraps any FastStream broker (RabbitBroker, KafkaBroker, NatsBroker, RedisBroker, etc.) with a uniform connect / disconnect / health-check surface matching the SDK's other backends, and forwards publish.     DeadLetterSpec dataclass ¶

    DeadLetterSpec(exchange: str, routing_key: str | None = None, queue: str | None = None)

    Where a rejected message goes.

    On RabbitMQ, dead-lettering is a property of the queue, not of the consumer: the broker routes a message to exchange when it is rejected without requeue, expires, or overflows the queue length. Without it, a rejected message is discarded — which is the default and is silent.

    Naming a :attr:queue makes the topology complete: the exchange and that queue are declared and bound before any subscriber starts, so a message rejected on the first delivery already has somewhere to go.     delivery_attempt ¶

    delivery_attempt(message: object) -> int

    Return which delivery this is, counting from 1.

    RabbitMQ records every dead-lettering in the message's x-death header, so the number of times a message has already been rejected is readable without any state of our own — which matters, because a consumer restart must not reset the budget.

    Entries whose reason is "expired" are skipped, and that is load-bearing rather than a detail. RabbitMQ keeps one entry per (queue, reason) pair, and the delayed-retry chain dead-letters a message twice per round: once out of the main queue (rejected) and once out of the retry queue when its TTL fires (expired). Summing every entry therefore advanced the counter by two per retry, so a max_attempts=3 policy gave up after two deliveries. An expiry is the waiting room emptying itself, not a delivery that failed.

    Build the delayed-retry topology for channel.

    RabbitMQ has no per-message delay of its own. The portable way to get one is a pair of queues: the main queue dead-letters a rejected message into a retry queue whose only job is to hold it, and that queue's TTL dead-letters it back to the main exchange when it expires. The message therefore reappears at the consumer delay_ms later, with the broker doing the waiting — so a worker restart in the meantime changes nothing.

    The alternative is the rabbitmq_delayed_message_exchange plugin, which is simpler to declare and requires the plugin installed — not available on several managed offerings, including the free CloudAMQP tier. This builds on stock AMQP instead.

    DeadLetterSpec dataclass ¶

    DeadLetterSpec(exchange: str, routing_key: str | None = None, queue: str | None = None)

    Where a rejected message goes.

    On RabbitMQ, dead-lettering is a property of the queue, not of the consumer: the broker routes a message to exchange when it is rejected without requeue, expires, or overflows the queue length. Without it, a rejected message is discarded — which is the default and is silent.

    Naming a :attr:queue makes the topology complete: the exchange and that queue are declared and bound before any subscriber starts, so a message rejected on the first delivery already has somewhere to go. Leave it None when something else consumes the exchange — the delayed-retry chain of :func:~tempest_fastapi_sdk.queue.retry_queues is the case: its retry queue is bound there, and a second queue under the same key would receive a duplicate of every failure.

    retry_exchange: str,

    dead_exchange: str,

    Build the delayed-retry topology for channel.

    RabbitMQ has no per-message delay of its own. The portable way to get one is a pair of queues: the main queue dead-letters a rejected message into a retry queue whose only job is to hold it, and that queue's TTL dead-letters it back to the main exchange when it expires. The message therefore reappears at the consumer delay_ms later, with the broker doing the waiting — so a worker restart in the meantime changes nothing.

    The alternative is the rabbitmq_delayed_message_exchange plugin, which is simpler to declare and requires the plugin installed — not available on several managed offerings, including the free CloudAMQP tier. This builds on stock AMQP instead.

    delivery_attempt ¶

    delivery_attempt(message: object) -> int

    Return which delivery this is, counting from 1.

    RabbitMQ records every dead-lettering in the message's x-death header, so the number of times a message has already been rejected is readable without any state of our own — which matters, because a consumer restart must not reset the budget.

    Entries whose reason is "expired" are skipped, and that is load-bearing rather than a detail. RabbitMQ keeps one entry per (queue, reason) pair, and the delayed-retry chain dead-letters a message twice per round: once out of the main queue (rejected) and once out of the retry queue when its TTL fires (expired). Summing every entry therefore advanced the counter by two per retry, so a max_attempts=3 policy gave up after two deliveries. An expiry is the waiting room emptying itself, not a delivery that failed.

    consume_span ¶
